# input

## summary
Unit "input" is the Windows-only input-injection and key-capture layer of the native engine, plus the shared wire enum it consumes. Four files: crates/input/src/lib.rs (293 lines) is the host-side injector. The Injector struct turns normalized InputMsg events into SendInput calls, using scan codes for keys and absolute mouse coordinates mapped into a shared display rectangle. It keeps a set of held keys and buttons so release_all can unstick input, and it tags every injected event with INJECT_SENTINEL (0x5343_5253, "SCRS") in dwExtraInfo. focus_window_at brings the window under a normalized point to the foreground without clicking. Windows code sits in #[cfg(windows)] mod imp (lib.rs:35-234) and focus_window_at (245-272). Non-Windows builds get a no-op stub Injector (283-293) and a false-returning focus_window_at (274-277). crates/input/src/keyhook.rs (313 lines, compiled only on Windows via lib.rs:12-13) is the viewer-side WH_KEYBOARD_LL hook. It suppresses Win keys always and Tab/Esc while Alt is held, but only while the session window is foreground (focus gate). It forwards each captured key through a boxed callback and synthesizes AltLeft down/up so the remote Alt+Tab switcher opens. It owes every forwarded key-up unconditionally to prevent stuck keys, and it ignores injected events by LLKHF_INJECTED or the sentinel. crates/input/src/scancode.rs (321 lines) is fully OS-agnostic: a DOM KeyboardEvent.code to Windows Set-1 scan code table (lookup, lines 16-138) and its inverse code_for (143-154). The wire format is the layout-independent DOM code, so this table is the only host-side key-to-OS mapping. The viewer uses the inverse table (pipeline.rs:988, per grep) to turn captured Win32 scancodes back into DOM codes. crates/protocol/src/input.rs (98 lines, OS-agnostic serde) defines Button (0/1/2, matching DOM MouseEvent.button) and the InputMsg tagged enum with wire tags mm/md/mu/wh/kd/ku. Coordinates are normalized floats in [0,1], top-left origin of the full captured screen (input.rs:38).

- Caller: pipeline.rs:988 calls input::scancode::code_for(scancode, extended) to convert captured Win32 scancodes to DOM codes on the viewer side before forwarding.
- Wire: InputMsg is serialized as one JSON object per data-channel message (input.rs:1-6). mm rides the unreliable channel, throttled to at most 60 msg/s by the sender. All other types ride the reliable channel, because a lost key-up or mouse-up would leave stuck input. The host ignores all of these unless the current permission is `control` (input.rs:2-3). That gate is in the engine, not in these files.
- Threading: Injector is documented as single-threaded, driven from one engine input thread (lib.rs:51-52). It has no internal locking. Its HashSets are mutated only from that thread.
- Global state shared across threads: keyhook STATE, HOOK_HELD, SYNTH_ALT and FOCUS_ROOT (see gotchas for the locking order). The forward closure is invoked while STATE is held, so it runs on the hook thread and must not block or call install/uninstall.
- Ownership: the Injector owns the bookkeeping (held keys and buttons). Nothing outside it can release a key without going through release_all (lib.rs:217). Keyhook owns its HHOOK as a raw isize (keyhook.rs:37-38, 266, 282).

## gotchas
- SendInput cbSize must be size_of::<INPUT>(); the comment says SendInput silently returns 0 otherwise (lib.rs:97-98, 212). The return value of every SendInput call is discarded (lib.rs:99, 212), so a blocked injection (for example UIPI, since higher-integrity windows reject input) fails silently. A port should decide whether to surface errors. The code never checks for them.
- Absolute mouse, primary path (no target rect): plain MOUSEEVENTF_MOVE|ABSOLUTE over the [0,65535] range, with no VIRTUALDESK flag, so it maps to the primary display only (lib.rs:106-115). Target path: converts normalized to physical px as t.x + nx*t.w, normalizes against the virtual desktop with denominator (vw-1)/(vh-1), and adds VIRTUALDESK (lib.rs:137-146). The fallback to primary happens if virtual size is <=1 (lib.rs:126-134). Multiply is done in f64 to avoid overflow (lib.rs:136). Note the asymmetry: the primary path uses 65535 directly and does not subtract 1.
- mouse_move does not clamp nx/ny (lib.rs:106-147), so out-of-range input projects outside the target rect. Rust's f64-to-i32 `as` cast saturates, and NaN becomes 0. focus_window_at does clamp (lib.rs:259-260). Input validation for coordinates is not present in input.rs either (protocol/input.rs:37-38 only documents the range).
- mouse_button moves to (nx,ny) first and only then sends the button edge (lib.rs:161-164). The comment says this makes the click land even if an earlier mm was dropped, because mm is unreliable. down_buttons is updated before the move (lib.rs:155-160).
- wheel() sends dy (MOUSEEVENTF_WHEEL) before dx (HWHEEL) and skips zero deltas (lib.rs:169-176). mouseData is a u32, and the signed delta is cast bit-for-bit (lib.rs:171, 174, comment 167-168). The protocol says units are multiples of 120 (protocol/input.rs:52). The Injector does not validate that.
- key(): unknown codes return before any state change (lib.rs:181-183). Key-up for an unknown code is therefore never tracked, and an unknown key-down is never tracked either. A key is recorded in down_keys only after it resolves to a scan code (lib.rs:184-188). emit_scancode sets KEYEVENTF_SCANCODE, adds EXTENDEDKEY when ext is set, adds KEYUP on release, sets wVk=0 and wScan=sc (lib.rs:192-213). The Set-1 code is the only key identity sent; the layout is not consulted.
- release_all drains down_keys and down_buttons and sends the up events with no preceding move, so the cursor stays where it is (lib.rs:215-232, comment 215-216). The button match skips unknown ids (`_ => continue`, lib.rs:228). Iteration order of HashSet is nondeterministic, so the order of releases varies run to run.
- The viewer-side hook proc ignores any event whose LLKHF_INJECTED flag is set or whose dwExtraInfo equals INJECT_SENTINEL (keyhook.rs:131-135). The injector's own events are therefore filtered, which prevents feedback loops (lib.rs:19-22, keyhook.rs:14-15). The sentinel is also the only way to distinguish our events on a local loopback test.
- Hook proc, per keyhook.rs:148-164 (stuck-key invariant): once a key-DOWN has been forwarded (recorded via hook_held_insert, keyhook.rs:197-199), its matching key-UP is forwarded unconditionally, even if should_suppress no longer holds (for example, Alt released before Tab). This is the stated reason the release path does not re-check the suppress conditions. Local suppression of the up is applied only when should_suppress && session_focused (keyhook.rs:158-160).
- Synthetic AltLeft: the first Tab or Esc key-down while SYNTH_ALT is false synthesizes AltLeft-down for the remote (keyhook.rs:187-196), so the remote switcher opens. The real Alt-up resets SYNTH_ALT and forwards AltLeft-up, and this happens before the suppression logic and is never suppressed locally (keyhook.rs:141-146). uninstall() clears SYNTH_ALT and HOOK_HELD without sending any release, relying on the host to release everything at session end (keyhook.rs:273-287, comment 277).
- Focus gate: suppression applies only when the session window is foreground (keyhook.rs:169-177; FOCUS_ROOT is the top-level ancestor of the child HWND set via GetAncestor, keyhook.rs:55-69). A key-down that matches but is not focused falls through to CallNextHookEx. The comment on FOCUS_ROOT (keyhook.rs:47-50) describes the gate as active only while foreground. Its phrase '0 = gate open never' (keyhook.rs:50) reads as the gate never opening, which matches the code (session_focused returns false when root==0, keyhook.rs:74-77).
- Locking and reentrancy: forward_key locks STATE and calls the forward closure while the lock is held (keyhook.rs:231-238). install() and uninstall() also lock STATE (keyhook.rs:245, 279). The hook proc takes STATE on every forwarded key, so a forward closure must never call install/uninstall (deadlock), and must not block for long, because Windows enforces a hook timeout (keyhook.rs:10-12). Keep this order if porting: the callback runs on the pump thread, and uninstall runs on the same thread after the pump returns (pipeline.rs:946-947, per grep).
- Install is idempotent: if hook != 0 it just swaps the forward closure and returns true (keyhook.rs:249-252). Install failures return false silently, and the feature is disabled (keyhook.rs:259-265, 262 logs a warning). uninstall is safe to call when not installed (keyhook.rs:273 doc).
- tracing::debug! calls run inside the low-level hook proc (keyhook.rs:172-175, 178-181). Logging on the hook path adds latency to every captured key, and the 300 ms timeout is a hard constraint that a port must respect.
- message_pump is a PeekMessageW busy-loop with a 10 ms sleep (keyhook.rs:297-313), so hook callbacks can be delayed by up to about 10 ms. The pump exits only when stop is set, and it checks stop only between sleeps.
- focus_window_at picks the top-level window (GA_ROOT) rather than the child under the point (lib.rs:266-270), and it is focus-only so that a real drop does not press a button on the target (lib.rs:239-244). The clamp on nx/ny and the w/h max(1) guard (lib.rs:256-260) are both present.
- Non-Windows stub: lib.rs:283-293 Injector has only new, set_target_rect, dispatch and release_all as no-ops. The stub does not provide mouse_move/mouse_button/wheel/key, so it compiles only as long as nothing outside calls those methods directly. scancode.rs compiles everywhere (lib.rs:14 is not cfg-gated), so its tests run on any host (lib.rs:279-280 comment).
- scancode table invariants: sc == 0 is used as the 'not found' sentinel in lookup (scancode.rs:18-106 `_ => 0`, 107-109), so no real key may map to 0. The table is duplicated: ALL_CODES (scancode.rs:157-262) is a hand-maintained list of every code, and it must match the two match arms. The comment at scancode.rs:144-145 calls the match arms the single source of truth, but code_for uses ALL_CODES, so drift is possible. Both lists currently hold 104 entries (86 non-extended, 18 extended), which the reading confirmed.
- code_for is linear: it calls lookup for every entry of ALL_CODES on each call (scancode.rs:146-152). On the viewer capture path (pipeline.rs:988, per grep) that is a per-key O(104) scan with no cache.
- Unsupported keys by design (scancode.rs:14-15, 359-366 tests): Pause, media keys and Fn return None. The list also omits NumpadEqual, IntlRo, IntlYen, Lang1/2 and other less common DOM codes. Unknown codes are dropped silently at both host and viewer.
- Test weakness in protocol/input.rs:79-98: button_roundtrip calls matches! but does not assert on the result, so it never fails if the variant is wrong (the bool is discarded at line 90). Only the field checks at lines 87-88 do any work.
- Wire shape is a serde internally-tagged enum with tag "t" and renamed variants (protocol/input.rs:39-61). Button is serialized as a numeric u8 via try_from/into (protocol/input.rs:11-12), so unknown button ids fail deserialization rather than reaching the injector. That gate is in serde, not in the Injector.
