# plans-00-02-03 (protocol contract + old electron client plan + hosting)

## summary
Scope and framing: the three documents read are the protocol contract (00-OVERVIEW-AND-PROTOCOL.md, 320 lines), the Electron client plan (02-PLAN-CLIENT-APP.md, 403 lines) and the hosting plan (03-HOSTING.md, 83 lines). All three are Electron/Cloudflare-era planning docs. 00 defines the wire protocol (WebSocket JSON signaling plus WebRTC data-channel input and control). 02 is the desktop client design: the Electron main process (Node) handles config, IPC, screen-source selection and Win32 SendInput via koffi, and the renderer (Chromium) handles UI, WebSocket, RTCPeerConnection and capture. 03 places the signaling server on Cloudflare Workers plus Durable Objects, with Google STUN and optional TURN. The protocol and renderer logic in 00 and 02 is OS-agnostic. The only Win32 surface is user32.dll SendInput in 02 section 7 (input.js, the only file that touches koffi, 02:33). Screen capture goes through Electron desktopCapturer and setDisplayMediaRequestHandler (02:76-86). That is portable Electron API, but its display selection is written around Windows display ids. Packaging is Windows-only (nsis/portable, 02:21 and 02:399-403). Scope note for the parent: this is the superseded Electron design. pans/04-NATIVE-REWRITE-PLAN.md (outside this unit) is the native-rewrite plan, and the live code is Rust/Tauri, so these citations map the protocol contract and the old client design, not the current Rust source. Protocol shape (00): text-frame JSON over wss. The server registry is keyed by UUID v4, and the from field comes from the registry (00:80-83). Liveness is a byte-exact ping/pong literal pair every 25 s (00:179-186). The connect handshake is connect-request, then password-required (challenge) or connect-response, then SDP offer/answer and trickle ICE via signal messages, with the host as offerer (00:98-161). Two data channels are created by the host: ctl (ordered, reliable: md, mu, wh, kd, ku, perm, bye) and mm (unordered, maxRetransmits 0: mouse move only) (00:196-216). The host ignores all input unless permission is control (00:207). Password is challenge-response: proof = SHA256(SHA256(plain) + ':' + nonce), and the host stores SHA256(plain) (00:132-137). Client design (02): one BrowserWindow, 1050x720, with CSP and a sandboxed preload (02:91-100). Five IPC channels are validated in main (02:104-113). Config JSON lives in userData with an atomic tmp-then-rename save (02:48-63). Host flow steps 1-9 (02:264-303), viewer flow steps 1-6 (02:305-326), viewer input capture with letterbox mapping, rAF-coalesced mm, wheel sign flip and a stuck-key Set (02:328-358), reconnect and ping logic (02:244-258), and seven milestones M1-M7 with gates (02:360-371).

## platform_deps
- **user32.dll SendInput via koffi: koffi.load('user32.dll'), SendInput(uint32, INPUT*, int)** @ 02:18, 02:153-167, 02:183-196; implemented in main/input.js (02:33)
  - purpose: Inject synthetic mouse and keyboard events into the host OS
  - portable: Contract: one synchronous call per event; cbSize equals the struct size (40 on x64, asserted at load, 02:165-166). Mouse uses ABSOLUTE normalized coords 0..65535 mapped to the PRIMARY display only (02:185-187). Keys use the SCANCODE flag with wVk=0 and EXTENDEDKEY for the ext table (02:195-196). Events must stay in order. A macOS or Linux replacement must post equivalent OS-level events (for example CGEvent on macOS, XTEST or uinput/portal on Linux; this OS mapping is platform knowledge, not in the docs) and reproduce the same four-function semantics. Failure is silent: SendInput's return value is never checked (02:187-196), and UIPI drops input silently (02:376-378).
- **INPUT, MOUSEINPUT, KEYBDINPUT, HARDWAREINPUT struct layout and MOUSEEVENTF_/KEYEVENTF_ flag constants** @ 02:151-181
  - purpose: Build the Win32 ABI payload
  - portable: Pure Win32 ABI. Only the logical event kinds carry over: move, button down/up, wheel, horizontal wheel, key down/up with extended flag.
- **Windows Set 1 scan-code table keyed by DOM KeyboardEvent.code (non-extended 02:200-225, extended 02:229-239)** @ 02:198-242
  - purpose: Map physical keys to Windows scan codes, layout-independent
  - portable: The DOM code list is portable; the sc values are Windows-only. macOS and Linux need their own DOM-code to native-keycode map. The table has no F13-F24, IntlRo/IntlYen or Lang keys. Pause (E1 prefix), media keys and Fn are deliberately ignored (02:241-242).
- **Wheel units in multiples of 120 (WHEEL_DELTA) and int32 mouseData for negative deltas** @ 00:214; 02:191-193; 02:347-350; 02:213 (clamp to ±1200)
  - purpose: Scroll events on the host
  - portable: Viewer sends ±120 per DOM wheel event with Y sign flip (02:348-349). macOS scroll is pixel or line based and Linux X11 uses button 4/5 clicks, so the host backend must convert units and direction. Natural-scroll direction is an explicit acceptance criterion (02:368).
- **Primary-display-only targeting: absolute coords map to the primary display; no VIRTUALDESK, no DPI math** @ 02:185-187; 02:112 (screen:size = primary display physical px x scaleFactor); 02:389-392 (gotcha 7)
  - purpose: Keep capture and injection coordinate spaces consistent
  - portable: Contract: normalized [0,1] in, primary display out. The replacement must target the same display desktopCapturer captures, and one side must not change without the other (02:391-392).
- **Electron desktopCapturer plus session.setDisplayMediaRequestHandler (useSystemPicker:false); picks the source whose display_id equals String(primary display id), falls back to sources[0]** @ 02:19; 02:76-86; 02:378-380
  - purpose: Host screen capture without a picker
  - portable: Electron-level API, portable in principle, but display_id matching is written around Windows display ids. The docs do not address Linux or Wayland, where display_id may be empty (inference). On macOS, screen capture needs a Screen Recording permission grant (platform knowledge, not in docs). The handler must always call callback, including callback({}) in catch (02:84-86), or getDisplayMedia hangs forever.
- **app.getPath('userData') for config.json, and --profile via app.setPath before whenReady** @ 02:50; 02:67-72
  - purpose: Per-user config location and a second instance on one machine
  - portable: Path is OS-specific (Windows AppData-style). The API is portable; the on-disk location differs by OS. --profile must run before whenReady and must not use requestSingleInstanceLock (02:72).
- **fs.renameSync used as atomic replace for config.json (write .tmp then rename over the original)** @ 02:58
  - purpose: Crash-safe config save
  - portable: Atomic replace-over-existing is natural on POSIX. On Windows, rename over an existing file can fail if another process holds it open (platform knowledge, not stated in docs). A replacement must keep the write-temp-then-replace contract on each OS.
- **koffi native module loading and asar packaging (asarUnpack **/node_modules/koffi/**)** @ 02:18; 02:374-375; 02:402
  - purpose: Native binary must load from disk, not from inside asar
  - portable: koffi is needed only for the Windows backend. On macOS and Linux the input backend needs a different mechanism. asarUnpack already covers all koffi platform binaries.
- **Packaging targets: win.target nsis plus portable; no mac or linux targets; no code signing (SmartScreen warnings expected)** @ 02:21; 02:370 (M7 gate: packaged app still injects input); 02:399-403
  - purpose: Installers and distribution
  - portable: The doc has no mac or linux build section. macOS and Linux packaging, signing and entitlements are absent. The M7 gate is Windows-only by definition.
- **OS-reserved shortcuts: Alt+Tab, Ctrl+Alt+Del, Win+L cannot be captured; MetaLeft/MetaRight mapped to Windows key codes 0x5B/0x5C; F11 passed through intentionally** @ 02:355-356; 02:238; 02:354

## cross_module_contracts
- Renderer to main: ipcRenderer.invoke through the preload 'native' API only (02:117). Handlers check event.senderFrame === win.webContents.mainFrame (02:104). input:inject is fire-and-forget from the renderer (02:297-298), and main must re-validate its shape (02:113).
- Renderer to server: WebSocket text frames, one JSON object per frame; relay rules and from field from the server registry (00:76-83).
- Viewer to host peer: WebRTC. The host creates two data channels before createOffer (02:282-283) with fixed labels and options (00:199-202). Video is one sendonly track from getDisplayMedia (02:276-284). The viewer receives via ondatachannel and ontrack (02:315-318).
- Host config is read on every connect-request (02:139-144, 02:268-270); a changed mode applies to the next request only.
- Threading and timers: Electron main is a single Node event loop running IPC handlers, config I/O, desktopCapturer and koffi SendInput calls. The renderer is a single Chromium event loop running UI, WebSocket, RTCPeerConnection, the rAF coalescing loop (02:341), the 25 s ping interval (02:248), the 10 s pong watchdog, reconnect backoff timers (02:252), the 30 s viewer request timer (02:307), the 30 s host popup countdown (02:271) and the 8 s disconnected grace (02:301). Chromium media and WebRTC threads are internal.
- Global and static state: main process module-level koffi user32 handle, struct types and SendInput binding (02:153-166); BrowserWindow reference win used by IPC guards (02:104); config object loaded from disk (02:48-63). Renderer: one global state variable (02:123); signaling WebSocket and reconnect counter (02:244-258); pc, ctl, mm, stream, track and local permission variable per session (02:276-303); viewer stash of channels by label (02:316); viewer Set of pressed codes (02:357); latest {nx,ny} coalescing buffer (02:341).
- Persistence: config.json, config.json.tmp and config.json.bad under userData (02:50, 02:55, 02:58). No other disk state. The server stores nothing (00:64-67).

## gotchas
- G1 password protocol mismatch (02:110-111, 02:61-63, 02:273-274 vs 00:132-137). The client plan still describes v1 plaintext compare: verifyPassword(plain) hashes its argument and compares with passwordHash, and host step 4 passes msg.password (a proof under v1.1) into it. The doc never says how the host computes or checks proof = SHA256(SHA256(pw) + ':' + nonce), nor where the nonce is stored. A correct implementation must store the issued nonce per pending attempt and verify only against that nonce.
- G2 nonce lifecycle is unspecified (00:126-127, 00:132-137). The docs do not say whether the nonce is single-use, expires, or is bound to the requester's UUID. Without that, a captured proof could be replayed while the same nonce is still accepted. passwordHash is also password-equivalent for proof computation, so anyone with config.json can compute valid proofs.
- G3 negotiation is not a state (02:123-133, 02:266, 02:276-296). Host state stays READY through password-required, getDisplayMedia and offer creation (steps 4-5), and only becomes HOST_ACTIVE on ctl.onopen (02:295). The busy check (02:266) therefore does not block a second connect-request during negotiation. The state table has no ACCEPTING or NEGOTIATING state.
- G4 host drops key-up on permission downgrade (02:296-298 vs 02:357-358 and 02:299). Host step 7 drops every input message when permission is view, including ku. The viewer sends ku for held keys when permission changes (02:357-358), which the host ignores, so keys can stay down on the host. The doc has no host-side release of its own pressed keys or buttons on permission drop or session end (02:301-303).
- G5 mouse button state is not tracked on focus loss. 02:357-358 covers only the key Set on blur, permission drop and teardown. A held mouse button (md without mu) is never released, so the host can keep a button down.
- G6 mm (unordered) can arrive after md or mu on ctl (00:196-205, 02:341-346). The doc handles a lost mm by carrying coords in md and mu (02:384-385), but a stale mm arriving late can move the cursor after a click or drag start. No ordering or sequence number is specified.
- G7 input:inject must reach SendInput synchronously. Fire-and-forget IPC (02:297-298) plus per-call async handlers preserves event order only if the handler does no await before the koffi call. The doc does not state this invariant.
- G8 caps are dropped. 00:112-116 says the viewer may send caps.decode and the host should use it to pick a codec, but 02:9.2 step 1 sends connect-request {to,password} with no caps, and 02:9.1 step 5f orders codecs AV1, VP9, H264 regardless of viewer capability.
- G9 wheel quantisation. Every DOM wheel event with a non-zero delta becomes exactly ±120 (02:348-349), regardless of magnitude, deltaMode (lines vs pixels) or fine trackpad deltas. Trackpads produce many full notches.
- G10 register-error handling is partial. 02:255-256 handles only duplicate; invalid-uuid and bad-version (00:91) have no client behaviour.
- G11 key coverage gaps: F13-F24, IntlRo, IntlYen, Lang1, Lang2 and similar are not in the table (02:198-239) and are silently dropped (02:195: unknown code returns silently).
- G12 SendInput failure is unchecked (02:187-196). UIPI and elevated targets silently no-op (02:376-378, 00:269-272). No detection or UI is specified; the only guidance is run as administrator.
- G13 Windows-only wording: Win key mapping (02:238), Alt+Tab, Ctrl+Alt+Del, Win+L limits (02:355-356), run as administrator (02:378, 00:272). Each needs per-OS wording.
- G14 getDisplayMedia hangs if the handler throws (02:84-86, 02:380). The handler must always resolve.
- G15 The ping must be the 15-byte literal {"type":"ping"} (02:248, 02:386-389). Any re-serialisation breaks the server auto-responder and wakes the Durable Object.
- G16 Single-session invariant: 00:47-48 says one active session per app. Only the busy reply enforces it, with the G3 caveat.
- G17 Multi-monitor: v1 captures and injects the primary display only (02:185-187, 02:391-392). Changing one side breaks coordinates.
- G18 Tuning calls are each wrapped in try/catch, and the app must still work if all fail (02:285, 02:378-382; 02:384 note 4).
- G19 jitterBufferTarget=0 is set on the viewer receiver after ontrack, inside try/catch (02:318). Tuning only.
- G20 A signaling drop does not end an active session, because WebRTC is independent of the socket (02:254). Teardown triggers are peer-level only (02:299-303, 02:325).
- G21 Config atomic write uses rename over an existing file (02:58). On Windows this can fail when the file is locked; a replacement must keep the same semantics.
