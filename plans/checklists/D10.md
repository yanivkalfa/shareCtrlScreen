# D10 — viewer cursor feels instant on a high-latency link: tester checklist

What this proves: when you CONTROL a remote machine over a relayed / high-RTT link, the
pointer feels immediate — there is **one** cursor that tracks the real mouse with no
trailing second cursor and no visible lag gap, and it still shows the host's real cursor
SHAPE (arrow, I-beam, hand, resize). The OS cursor is hidden over the video while you
control and comes back the instant the pointer leaves the video or the window loses focus.
A **view-only** session is unchanged: it still shows the host's own cursor moving (the
out-of-band position), because that is the only position it has.

Before D10 the drawn sprite followed the host's echoed out-of-band position (a full round
trip behind on a relay) while the controller's own OS cursor sat at the real mouse — two
cursors, the gap between them = the latency. D10 draws the sprite at the LOCAL pointer
while controlling (client-side prediction, like AnyDesk/RDP) and hides the OS cursor, so
there is one cursor at the real mouse. **Only the position source changed — the shape is
still the host's (D9).**

None of the hide/restore feel can run on a CI runner (it needs a GUI session and a real
relayed link). What **is** covered on every OS by `cargo test`:
* the position-source selection — `crates/engine/src/media/viewer.rs`
  (`cursor_position`: control + pointer over the video -> local; view-only or pointer not
  over the surface -> host; host cursor invisible -> nothing drawn);
* the local-pointer gating — `crates/surface-wgpu/src/state.rs`
  (`SurfaceState::local_pointer`).

## Before you start

* **Two machines on a relayed path.** The effect only shows with real latency: use a TURN
  relay or two machines on different networks (the native-test-setup). On a LAN the old
  behaviour already looked fine, so a LAN test proves nothing.
* **Builds:** the D10 viewer build on the controller; any host build on the other machine.
  Test each viewer OS you can (Windows, macOS, Linux X11, Linux Wayland).
* **Grant control**, not view-only, for steps 1–5 (view-only is step 6).
* **Logs:** controller `app.log` (Windows `%APPDATA%\ShareCtrlScreen\logs`, macOS
  `~/Library/Logs/ShareCtrlScreen/app.log`, Linux `~/.local/state/...` / stderr). The key
  line is `key translation:` / session start; there is no per-frame cursor log.

For each step write **pass / fail**; for a fail attach a short screen recording of the
controller (a still cannot show the lag gap) and the log around it.

## 1. One instant cursor while controlling (the core fix)

1. Connect with **control** and let the remote picture fill the window.
2. Move the mouse in a fast circle over the video.
   Expected: exactly ONE cursor, riding the real mouse with no perceptible lag and no
   second cursor trailing behind it. (Before D10 you would see a second cursor lagging by
   the round-trip time.)
3. Stop the mouse.
   Expected: the single cursor is exactly under the physical mouse, not offset.

## 2. The host shape is preserved (D9 not regressed)

1. Move over a text field / terminal on the remote: the cursor becomes an **I-beam**.
2. Move over a window edge / link: it becomes the **resize** / **hand** shape.
3. Over an app that shows a custom cursor, that cursor shows.
   Expected: the shape is always the host's real cursor image; only its position is
   instant. If the host ever sends no image (older host), a plain arrow is drawn instead —
   still at the instant local position.

## 3. The OS cursor is hidden over the video, and comes back

1. While controlling, look closely: there is no duplicate OS arrow next to the sprite.
2. Move the pointer OFF the video — onto the title bar, the revealed toolbar strip
   (hover the top edge), or another window.
   Expected: the normal OS cursor is there immediately (the toolbar buttons show the arrow
   and are clickable).
3. Move back onto the video.
   Expected: the OS cursor hides again; one instant cursor.

## 4. Focus loss restores the OS cursor; nothing sticks hidden

1. While controlling with the pointer over the video, switch away from the app:
   * **macOS:** Cmd+Tab to another app (or click another app).
   * **Windows:** Alt+Tab away, or click another window.
   * **Linux:** switch workspace / focus another window.
   Expected: the OS cursor is visible again immediately.
2. Switch back to the session (Cmd+Tab / Alt+Tab / click the video).
   Expected: the OS cursor hides again over the video; one instant cursor.
3. Repeat the away/back cycle ~10 times quickly, then disconnect.
   Expected: the OS cursor is ALWAYS visible after you leave the app, and after
   disconnect — it must NEVER be stuck invisible anywhere on the desktop. (This is the
   balance check for macOS `NSCursor::hide`/`unhide`.)

## 5. End of session restores the OS cursor

1. While controlling with the pointer over the video, press **Disconnect** / **End
   Session**.
   Expected: the home screen shows and the normal OS cursor is present at once.
2. Open **Settings** over a live session (if available) — the modal and the page show the
   normal cursor.

## 6. View-only still shows the host's cursor moving

1. Connect **view-only** (or have the host revoke control mid-session — see step 7).
2. Watch the remote cursor while the host-side user moves their mouse.
   Expected: the viewer shows the host's cursor moving (the out-of-band position), with
   the correct shape, and the OS cursor over the video is the normal arrow (not hidden) —
   exactly the pre-D10 behaviour. There is no "local pointer" to predict here.

## 7. Mid-session permission flip

1. Start with **control**; confirm the instant single cursor (step 1).
2. Have the host switch you to **view-only**.
   Expected: the drawn cursor switches to following the host's position, and the OS cursor
   comes back over the video.
3. Have the host grant **control** again.
   Expected: the instant single cursor returns and the OS cursor hides over the video.

## Per-OS notes

* **macOS:** the hide is `NSCursor::hide`/`unhide`, balanced on enter/leave and on every
  focus change (including Cmd+Tab away via `windowDidResignKey`), so step 4 is the key
  one — nothing may stay hidden.
* **Windows:** the hide is `WM_SETCURSOR` -> `SetCursor(NULL)` in the client area; it is
  pointer-driven, so leaving the client area (or the toolbar strip, which belongs to the
  web view) shows the normal cursor by itself.
* **Linux X11:** the hide swaps the window's cursor attribute to a transparent cursor.
  **Known caveat:** because the X11 cursor is a per-window attribute, it hides whenever you
  control regardless of keyboard focus — so if you focus another window while the pointer
  still sits over the video, the video area shows no cursor until control ends. Note
  whether this is acceptable; the pointer over any other window is unaffected.
* **Linux Wayland:** there is no portable way to hide the OS cursor, so the OS cursor
  stays visible and the predicted sprite is drawn at the SAME local position — they
  coincide, so there is still no lag gap (just possibly a doubled image exactly on top of
  itself). Confirm the sprite tracks the real mouse with no trailing gap.
