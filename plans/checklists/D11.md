# D11 — controller cursor no longer freezes between video frames: tester checklist

What this proves: when you CONTROL a remote machine and the host screen is **static** (so few
or no video frames arrive), the drawn cursor still tracks your real mouse **smoothly** — it
does NOT freeze for a second or two and then snap forward when the next frame finally arrives.
The host's real cursor SHAPE is still shown (D9), view-only still shows the host's own cursor,
and nothing vanishes when the host's cursor report momentarily blips.

Before D11 the sprite was repainted ONLY when a new video frame was presented. On a static
screen (an idle desktop, a still document, a paused video) the host sends few or no frames, so
the local pointer kept moving while the sprite sat still — "the cursor freezes several seconds,
then renders correctly." D10 made it obvious: the sprite follows the local pointer and the OS
cursor is hidden, so the gap showed as a dead cursor. D11 repaints the held last frame on a
~60 Hz idle tick whenever the cursor moved, so the cursor tracks even with no new frames.

This is a relay / high-RTT feel fix on a STATIC screen; it cannot run on a CI runner (needs a
GUI session and a real link). What **is** covered on every OS by `cargo test`:
* `crates/engine/src/media/viewer.rs` `cursor_position` unit tests — including the new D11
  fixed quadrant `controlling_over_the_video_survives_a_host_cursor_blip`
  (`control=true, local=Some, host=None` -> `Some(local)`), the reworked view-only invisible
  case, and the three unchanged D10 quadrants;
* the loopback integration test (`cargo test -p engine --test loopback --features test-hooks`,
  run x3 in the lane) still proves decode -> present end to end with the held-frame present loop.

## Before you start

* **Two machines on a relayed path** (TURN relay or two different networks — the
  native-test-setup). A LAN hides the problem.
* **A D11 viewer build** on the controller; any host build on the other machine.
* Test each viewer OS you can: Windows, macOS, Linux X11, Linux Wayland (the re-present loop is
  shared across all of them).
* **Grant control** (not view-only) for steps 1–4; view-only is step 5.
* **Make the host screen static:** on the host, open a still image or a plain document and do
  not touch the host mouse/keyboard, so the host sends essentially no new frames.

For each step write **pass / fail**; for a fail attach a short screen recording of the
controller (a still cannot show a freeze) and the controller `app.log` around it.

## 1. Cursor tracks smoothly on a static host screen (the core fix)

1. Connect with **control**; let the picture fill the window; make the host screen static
   (step "Before you start").
2. Move your mouse slowly, then in a fast circle over the video, for several seconds WITHOUT
   doing anything on the host that would change the screen.
   Expected: the cursor follows your real mouse smoothly the whole time — NO multi-second
   freeze, no "stuck then snaps forward." (Before D11 it would sit still until the next frame.)
3. Hold the mouse still for a few seconds.
   Expected: the cursor sits exactly under the physical mouse; no drift, no flicker. (The loop
   does no extra repaints while the pointer is stationary.)

## 2. The host shape is still correct (D9/D10 not regressed)

1. Over a text field / terminal: the cursor is an **I-beam**; over a window edge / link:
   **resize** / **hand**.
   Expected: the shape is always the host's real cursor image, now also while the screen is
   static. An older host that sends no image draws a plain arrow — still tracking smoothly.

## 3. A host-cursor "blip" never makes the cursor vanish (the `cursor_position` fix)

1. While controlling with the pointer over the video, do something that briefly drops or
   suppresses the host's out-of-band cursor report — e.g. the host hides its own cursor (a
   full-screen video/slideshow on the host), or exercise a lossy link so the unreliable cursor
   channel drops updates.
   Expected: your cursor STAYS on screen at your real mouse position the whole time. It must
   NOT blink out / vanish and reappear. (Before D11 the sprite vanished whenever the host
   report was momentarily absent while controlling.)

## 4. Focus / control toggles keep the cursor on the pointer (Windows hardening)

1. **Windows controller:** while controlling with the pointer sitting over the video, Alt+Tab
   away to another app and then Alt+Tab straight back WITHOUT moving the mouse.
   Expected: on return the cursor is immediately at your real mouse over the video (not dropped
   to the host's last position). (This is the `pointer_inside` re-evaluation on focus regain.)
2. Have the host switch you view-only then back to **control** WITHOUT moving the mouse.
   Expected: when control returns, the cursor is at once at your real pointer over the video.
3. Other OSes: repeat the Alt+Tab-equivalent away/back a few times; confirm the cursor returns
   to the real pointer and nothing sticks.

## 5. View-only is unchanged

1. Connect **view-only** (or have the host revoke control).
2. Watch the remote cursor while the host-side user moves their mouse, including while the rest
   of the host screen is static.
   Expected: the viewer shows the host's own cursor moving (the out-of-band position) with the
   correct shape; when the host hides its cursor, nothing is drawn (there is no local pointer to
   predict). Exactly the pre-D11 view-only behaviour.

## 6. No regression when the screen IS busy

1. With **control**, play a video or scroll continuously on the host (a full frame stream).
   Expected: motion is as smooth as before D11; the cursor still tracks; no added latency or
   stutter from the idle path (it only runs when frames are NOT arriving).

## Per-OS notes

* **All OSes:** the re-present loop is shared (`engine/src/media/viewer.rs`); it holds the last
  decoded frame and repaints it with the current cursor at ~60 Hz only when the cursor moved.
* **Windows:** also hardened `pointer_inside` so a focus regain / control-on re-checks whether
  the OS pointer is over the video (step 4) instead of waiting for the next mouse move.
* **macOS / Linux:** cursor-hide behaviour is unchanged from D10; only the repaint cadence
  changed. On Wayland the OS cursor stays visible and coincides with the predicted sprite (D10).

## Result

Record per viewer OS: pass/fail for steps 1–6, the link type (relay / cross-network), and any
case where the cursor froze on a static screen, vanished on a host-cursor blip, dropped to the
host position after a focus/control toggle, or stuttered on a busy screen.
