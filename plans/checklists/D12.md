# D12 — video returns instantly after closing Settings mid-session: tester checklist

What this proves: when you are in a live VIEWER session and open the Settings modal (which hides
the native video so the web modal shows) and then CLOSE it, the video reappears **immediately** —
even when the host screen is **static** (a still image, a plain document, a paused video). Before
D12 the re-shown surface stayed **black** until the next decoded frame or a cursor move, which on a
static host screen could be seconds or never.

Why it happened: opening Settings calls `set_video_visible(false)` → `surface.hide()`; closing
calls `set_video_visible(true)` → `surface.show()`. But `show()` does not itself repaint — the
present loop (`crates/engine/src/media/viewer.rs`) paints only on a NEW decoded frame, and D11's
idle re-present fired only when the cursor moved. On a static screen no frame arrives, so the
surface sat black. D12 adds a one-shot `Shared.repaint_requested` flag set by `set_video_visible(true)`;
the idle tick re-presents the held last frame once (or, if nothing has decoded yet, asks the host
for a keyframe).

This is a GUI + real-session feel fix; it cannot run on a CI runner. What **is** covered on every
OS by `cargo test`:
* `crates/engine/src/media/viewer.rs` `should_idle_repaint` unit tests — repaints on a repaint
  request with a STATIONARY cursor (the D12 case), does NOT repaint without a request and a still
  cursor (D11 unchanged), repaints on a moved cursor without a request (D11 unchanged);
* the loopback integration test (`cargo test -p engine --test loopback --features test-hooks`,
  run x3 in the lane) still proves decode → present end to end with the held-frame present loop.

## Before you start

* **Two machines** (a relay / cross-network path matches the original report; a LAN is fine too —
  the fix is about a static screen, not the link).
* **A D12 viewer build** on the controller; any host build on the other machine.
* Test each viewer OS you can: Windows, macOS, Linux X11, Linux Wayland (the repaint signal and
  the present loop are shared across all of them).
* **Make the host screen static:** on the host, open a still image or a plain document and do not
  touch the host mouse/keyboard, so the host sends essentially no new frames.

For each step write **pass / fail**; for a fail attach a short screen recording of the controller
and the controller `app.log` around it.

## 1. Settings open → close returns the video instantly on a STATIC host screen (the core fix)

1. Connect (control or view-only); let the picture fill the window; make the host screen static
   (step "Before you start").
2. Open **Settings** (gear). Expected: the native video is hidden and the Settings modal shows.
3. Close **Settings**. Expected: the video reappears **immediately** — no black rectangle, no
   multi-second delay, even though the host screen has not changed. (Before D12 it stayed black
   until the next frame.)
4. Repeat open/close several times quickly. Expected: the video is back every time, instantly.

## 2. Same, but with nothing yet to repaint (keyframe fallback)

1. Open Settings very early — right as the session connects, before much has decoded — then close
   it. Expected: the video appears promptly once the first frame arrives (D12 requests a keyframe
   when there is no held frame to repaint), rather than staying black.

## 3. No regression when the host screen IS busy

1. With the host playing a video / scrolling continuously, open and close Settings.
   Expected: the video is there on close as before; motion is smooth; no added latency or flicker
   from the repaint signal (it only does extra work on the idle tick, which a busy stream rarely
   reaches).

## 4. D11 cursor tracking not regressed

1. Controlling, host screen static, do NOT open Settings: move the mouse over the video.
   Expected: the cursor still tracks your real mouse smoothly (D11), with the correct host shape
   (D9/D10). Holding the mouse still does no extra repaints (no flicker).

## 5. Host is unaffected

1. On the HOST side during a session, confirm normal operation: `set_video_visible` is effectively
   a no-op on the host (no viewer surface / no viewer `shared`), so nothing about hosting changes.

## Per-OS notes

* **All OSes:** the repaint signal (`Shared.repaint_requested`, set by `session::request_repaint`
  from `set_video_visible(true)`) and the idle-tick re-present are shared
  (`crates/engine/src/media/viewer.rs`, `crates/engine/src/session/mod.rs`,
  `crates/engine/src/lib.rs`). No platform-specific code changed.
* **macOS / Linux / Windows:** the surface `hide()`/`show()` and the presenter are the existing
  per-platform implementations, untouched by D12.
