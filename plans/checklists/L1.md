# L1 — Wayland capture: portal ScreenCast + PipeWire (real desktop)

Needs a Wayland session on each of: **GNOME 46** (Ubuntu 24.04), **KDE Plasma 6**, **Sway**
(xdg-desktop-portal-wlr). Packages: `pipewire`, `wireplumber`, `xdg-desktop-portal` and the
desktop's backend (`xdg-desktop-portal-gnome` / `-kde` / `-wlr`). Build deps:
`libpipewire-0.3-dev libspa-0.2-dev libclang-dev`.

Automated half (also what CI's T4 job runs under headless sway):
`cargo test -p platform-linux --test portal_capture -- --ignored --nocapture` with something
moving on screen (e.g. `glxgears`, a video, or `watch -n0.1 date` in a terminal). It captures
100 frames, then reopens and checks the restore token was replaced (single-use). It uses a
temporary `XDG_STATE_HOME`, so your real token is untouched.

Token file: `${XDG_STATE_HOME:-~/.local/state}/sharectrl/portal.token`. Logs: `app.log` in the
same directory; capture lines start with `portal:` and `pipewire:`.

## Every desktop (GNOME 46, KDE 6, Sway)
1. Delete the token file; start hosting from the app. One dialog (pick a monitor). The viewer shows
   the picture; `app.log` has `pipewire: format VideoFormat::BGRx …` (or BGRA/RGBx; record which)
   and `portal: capturing WxH` with the monitor's **physical** pixel size (also on a 2× scaled
   monitor — record both numbers).
2. Disconnect and host again: **no dialog** (the token was restored). On KDE record if a dialog
   reappears (known restore bugs 480235); the capture must still work after answering it.
3. Cancel the dialog (delete the token first): hosting stops with "screen capture permission
   denied", no token file is written, the app does not hang.
4. Leave the dialog unanswered for 2 minutes: it closes by itself and the host reports "nobody
   answered the screen-sharing dialog within 120 s".
5. Static screen for 30 s: `top` shows the app near idle (no frames encoded while nothing changes).

## Pointer (cursor metadata)
6. GNOME/KDE: `app.log` shows no `cannot request buffer metadata`; the viewer's pointer follows the
   host's, moves without video frames being sent (watch the AU counter in the log stay still while
   only the mouse moves), and changes shape over a text field (I-beam) and a window edge.
7. Look closely at the pointer's soft edges on the viewer: no dark fringe (the bitmap is assumed
   premultiplied — a dark or bright halo means that assumption is wrong for this compositor).
8. Move the pointer onto another monitor (multi-monitor host): it disappears on the viewer and
   comes back when it returns. A video player that hides the pointer hides it on the viewer too.
   (GNOME sends cursor id 0 while the pointer is off the monitor or hidden; on KDE record whether
   the pointer hides the same way — KWin's encoding is unverified.)
9. Sway: no cursor metadata exists there; the pointer is drawn inside the video (Embedded mode).
   Record that it is visible.

## Damage
10. Type in a small terminal window on an otherwise static screen; with `RUST_LOG=debug` record
    whether frames carry dirty rects (GNOME ≥ 44 and wlr emit `spa_meta_video_damage`; KDE may not).
    Either way the picture must be correct (no stale areas after scrolling, dragging windows).

## Recovery
11. Change the shared monitor's resolution while hosting: the viewer goes on at the new size within
    a few seconds (`portal: capture size … → …`), no new dialog.
12. GNOME: click "Stop sharing" in the top-bar indicator. Log: `portal: the desktop closed the
    screen-cast session` and `sharing was stopped from the desktop; not reopening it`; the hosted
    session ends (the viewer is disconnected) and no new session or dialog appears. Hosting again
    later restores from the token as in step 2.
13. `systemctl --user restart pipewire` while hosting: the capture recovers (`portal: reopening the
    screen-cast session from the token`, then `session rebuilt`) or ends with a PipeWire message;
    it must not hang or crash.
13a. Make the token unrestorable (KDE: restart the portal service; elsewhere edit one character of
    the token file), then restart PipeWire while hosting: the reopen shows a dialog. While it is up,
    the viewer can disconnect at once (no freeze) and the dialog closes by itself. Left unanswered
    for 2 minutes, the session ends with "nobody answered the screen-sharing dialog" and no further
    dialog appears.
14. Lock the screen and unlock: the picture resumes (record whether through a pause/resume or a
    new session).

## Environments without a portal
15. WSLg or a headless box: hosting fails at once with "screen sharing on Wayland needs the desktop
    portal: install and start xdg-desktop-portal …" (the unit test
    `no_portal_fails_with_an_actionable_error` covers this automatically in WSL).
