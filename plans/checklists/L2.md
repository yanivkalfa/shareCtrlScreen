# L2 — X11 screen capture: Linux tester checklist

What this verifies: the X11 capture backend (`native/crates/platform-linux`, `X11Capture`)
on a real desktop. CI only proves it against Xvfb/Xephyr. A real desktop adds things CI
cannot show: a compositor, real monitors, real cursors, and real CPU cost. Takes about
30 minutes.

Report back:
- the Ubuntu version and the desktop (GNOME on Xorg, KDE on X11, Xfce, …);
- the GPU and driver;
- the monitor setup (count, resolutions, which one is primary);
- **the full terminal output of every step** (copy-paste or a text file).

## 0. Setup (once)

1. Ubuntu 22.04 (or 24.04), logged in to an **X11** session. On the GDM login screen,
   click the gear and pick "Ubuntu on Xorg". Check it in a terminal:
   `echo $XDG_SESSION_TYPE` must print `x11`, and `echo $WAYLAND_DISPLAY` must print
   nothing.
2. `sudo apt install -y build-essential curl git xvfb xserver-xephyr x11-xserver-utils xterm`,
   then install Rust from `https://rustup.rs`.
3. Get the branch: `git clone … && cd shareCtrlScreen/native && git checkout task/L2`
   (or the branch the orchestrator names).
4. Build the tests once: `cargo test -p platform-linux --test x11_capture --no-run`.

## 1. Automated tests on this machine

`cargo test -p platform-linux --test x11_capture`

- Expected: all tests pass, with no `skipping:` lines except possibly
  `xwayland_is_refused` (it needs a Wayland login; step 6 covers it).
- Every capture in these tests asserts it is on the MIT-SHM path.

## 2. Displays

`cargo test -p platform-linux --test x11_capture -- --ignored --nocapture --test-threads=1 desktop_lists_displays`

- Expected: one line per monitor.
  - Ids look like `x11:DP-1`, `x11:HDMI-1`, `x11:eDP-1` (the connector names `xrandr`
    prints).
  - Each monitor's `x`, `y`, `width` and `height` match `xrandr --listmonitors`.
  - Exactly one line has `primary: true`: the monitor `xrandr` marks with `*`, or the
    one at `+0+0` if none is marked.
  - `scale` is `Xft.dpi / 96` (1.0 unless display scaling is on; 2.0 at 200 %).
- Then run `desktop_each_display_captures` the same way. Expected: `<id>: WxH ok` for
  every monitor.

## 3. Frame rate, CPU, idle screen (acceptance)

`cargo test --release -p platform-linux --test x11_capture -- --ignored --nocapture --test-threads=1 desktop_busy_then_idle`

1. **PHASE 1** (10 s): keep dragging a window in circles, or play a video in a window.
   - Expected: `=> NN fps` of **25 or more** (X11 has no vsync limit here; the host caps
     at 60).
   - `dirty` well under 100 % while you drag a small window.
   - Process CPU: report the number. The budget is **< 15 %** of one core at 1080p while
     busy.
2. **PHASE 2** (10 s): hands off, stop the video.
   - Expected: a large `idle` count, and `fps` near 0 (a clock or blinking text cursor
     gives a few frames).
   - Move the mouse during the last seconds: `pointer-only` goes up, `fps` does not.
   - CPU near 0.
3. **Compositor check (the key unknown).** Run phase 1 again while dragging a window
   with the desktop's compositor on (GNOME/mutter and KDE/KWin composite by default).
   - Report whether fps is still above 25. If it drops to near 0 while windows visibly
     move, root-window damage does not see the compositor's output on this desktop.
     Report it; that is a design issue for the orchestrator, not a test failure to work
     around.

## 4. Resolution change and monitor changes

1. While the busy test from step 3 runs, change the resolution in Settings → Displays and
   keep the change.
   - Expected: no panic.
   - The test keeps running after a short pause: it prints frames again, and the next
     frames have the new size. (It panics with `capture failed:` only if the rebuild
     itself fails. Report that.)
2. With two monitors: unplug the non-primary one during step 3.
   - Expected: the capture keeps running.
3. Plug it back. Swap which monitor is primary.
   - Expected: no panic.

## 5. Cursor

In the busy test's phase 2:
1. Hover over text: the I-beam shape is reported (`pointer-only` frames increase).
2. Play a full-screen video that hides the pointer. Report whether frames still come.
   The cursor should be reported invisible; the test only counts frames, so just report
   that nothing panicked.

## 6. Unsupported setups (refusal messages)

1. Log in to "Ubuntu" (Wayland) instead, then run
   `cargo test -p platform-linux --test x11_capture xwayland_is_refused -- --nocapture`.
   Expected: passes without `skipping:`. The capture refuses Xwayland with a message
   naming it.
2. Optional, only if easy: set the X server to depth 30 (`DefaultDepth 30` in an
   `xorg.conf` Screen section) and run step 2.
   Expected: `desktop_each_display_captures` fails with "the X server's screen format is
   not supported (depth 30 …)". It must not produce frames with wrong colours.
