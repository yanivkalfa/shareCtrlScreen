# L3 — Linux hardware encoder (VA-API + NVENC): tester checklist

What this verifies: the Linux host can encode H.264 on the GPU (Intel/AMD through
VA-API, NVIDIA through NVENC), and falls back cleanly where it cannot.
NVENC was already verified on machine A's WSL2 (GTX 1080 Ti); **VA-API has
never run on real hardware** — that is the main thing to test.

Log file: `~/.local/state/sharectrl/app.log` (search for `hardware encoder`).

## 0. Machine facts (write them down)

```bash
lsb_release -ds                     # Ubuntu 22.04 or 24.04
lspci -nn | grep -Ei 'vga|3d|display'
ls -l /dev/dri/                     # renderD128 … must exist
groups                              # must include `render` (or `video` on older distros)
```

Install the inspection tools (not needed by the app itself):

```bash
sudo apt install vainfo ffmpeg      # Intel also: intel-media-va-driver-non-free (iHD)
```

## 1. What the driver offers

```bash
vainfo 2>&1 | head -5               # first lines: "VA-API version: 1.NN"
vainfo 2>&1 | grep -E 'H264.*Enc'
```

Expected:

| Machine | `VA-API version` | H.264 encode lines |
|---|---|---|
| Ubuntu 24.04, Intel Gen9+ (iHD) | 1.20 or newer | `VAProfileH264Main : VAEntrypointEncSliceLP` and/or `…EncSlice` |
| Ubuntu 24.04, AMD (radeonsi) | 1.20 or newer | `VAProfileH264Main : VAEntrypointEncSlice` |
| Ubuntu 22.04 (any GPU) | 1.14 | lines may exist, **but the app must not use them** (decision #7) |
| NVIDIA proprietary | n/a or decode-only | none (NVENC is used instead) |

Paste the full `vainfo` output into the report.

## 2. Run the app as host and read the probe

Start the app, start hosting a session (or just open it — the probe runs the
first time the host side asks what it can encode). Then:

```bash
grep -E 'hardware encoder|VA-API|NVENC|libva' ~/.local/state/sharectrl/app.log
```

What each machine should log:

* **24.04 Intel/AMD** —
  `hardware encoder: VA-API on /dev/dri/renderD128 — Intel iHD driver … (VA-API 1.2x; H.264 Main, low-power EncSliceLP)`
  (AMD: `Mesa Gallium driver …`, `EncSlice`), and when a viewer connects:
  `VA-API encoder: … level 4.x 1920x1080 @30/1 fps, … kbps CBR, max QP 32, packed headers 0x3`.
* **22.04 (any GPU)** —
  `hardware encoder unavailable — VA-API: renderD128: libva 2.14 (VA-API 1.14) is older than 2.20 — hardware encode stays off …`.
  The session must then use the software codec (task D2) — or, until D2 lands,
  fail with "no H264 encoder on this system". It must **not** crash or hang.
* **No GPU / no libva installed** — `VA-API: libva.so.2 not loadable …` and the
  same fallback. The app must still start.
* **NVIDIA** — `hardware encoder: NVENC on NVIDIA GeForce … (driver API 1x.y; H.264 yes, HEVC yes)`.

## 3. Picture check (24.04 Intel/AMD, viewer on Windows)

Connect from the Windows machine and check, writing down yes/no for each:

1. A picture appears within ~2 s of connecting (first frame is an IDR).
2. Colours are right: open a page with pure red/green/blue/white/black blocks
   (e.g. a test-card image); no green/purple tint, blacks are black, whites are
   white (a washed-out or crushed image means a range mismatch — report it).
3. Small text (a terminal at 10 pt) stays readable while scrolling; the frame
   rate drops on a busy screen rather than the text turning to mush (QP floor).
4. Resize the viewer window smaller: the picture stays sharp and correctly
   proportioned (VPP is scaling on the GPU).
5. Leave the screen idle for 30 s: the log's `encoded+sent AU` lines and the
   network graph go quiet (no stuffing bits on a static screen).
6. Disconnect and reconnect three times: each reconnect shows a picture
   (forced IDR) and nothing in the log says `coded buffer overflow` or
   `driver produced idr=false`.

Keyframe accounting: `grep 'keyframes/5s' app.log` — "encoder-initiated" must
stay **0** (this encoder never inserts IDRs on its own).

## 4. Developer test on the device (needs a Rust toolchain)

```bash
cd native
cargo test -p platform-linux -- --ignored vaapi --nocapture
# keep the stream for inspection:
mkdir -p /tmp/l3 && SCT_DUMP_STREAM=/tmp/l3 cargo test -p platform-linux -- --ignored vaapi_device_round_trip
ffprobe -v error -show_entries stream=profile,level,width,height,pix_fmt,color_range,color_space /tmp/l3/vaapi.h264
ffmpeg -v error -i /tmp/l3/vaapi.h264 -f null - && echo DECODES_CLEANLY
```

Expected: the test passes; `ffprobe` shows `profile=Main` (or `Constrained
Baseline`), `width=1280 height=720`, `color_range=tv`, `color_space=bt709`;
`ffmpeg` prints nothing before `DECODES_CLEANLY`.

NVIDIA machines can run the NVENC round trip the same way (it runs by default,
no `--ignored` needed): `SCT_DUMP_STREAM=/tmp/l3 cargo test -p platform-linux nvenc -- --nocapture`.

**Colour matrix check (NVENC dump).** The last frame of `nvenc.h264` is a
pure-red IDR. Decode it and average the planes:

```bash
n=$(ffprobe -v error -count_frames -show_entries stream=nb_read_frames -of csv=p=0 /tmp/l3/nvenc.h264)
ffmpeg -v error -i /tmp/l3/nvenc.h264 -vf "select=eq(n\,$((n-1)))" -vsync 0 -frames:v 1 \
       -f rawvideo -pix_fmt yuv420p /tmp/l3/red.yuv
python3 -c "d=open('/tmp/l3/red.yuv','rb').read();w,h=640,360;y=d[:w*h];u=d[w*h:w*h*5//4];v=d[w*h*5//4:];print(sum(y)/len(y),sum(u)/len(u),sum(v)/len(v))"
```

Expected ≈ `63 102 240` (BT.709 limited). `81 90 240` means BT.601 — report
it. Machine A's GTX 1080 Ti gave exactly `63.0 102.0 240.0`.
