# L4 — Linux hardware decoder (VA-API + NVDEC): tester checklist

What this verifies: the Linux viewer decodes the host's video on the GPU
(Intel/AMD through VA-API, NVIDIA through NVDEC) and falls back to Cisco
OpenH264 cleanly where it cannot. NVDEC was verified on machine A's WSL2
(GTX 1080 Ti, driver 572.83): NVENC → NVDEC round trip, and every golden
stream bit-identical to FFmpeg. **VA-API decoding has never run on real
hardware** — that is the main thing to test (machine B, Ubuntu live USB).

Log file: `~/.local/state/sharectrl/app.log` (search for `hardware decoder`).

## 0. Machine facts (write them down)

```bash
lsb_release -ds                     # Ubuntu 24.04 (22.04 must fall back, see step 2)
lspci -nn | grep -Ei 'vga|3d|display'
ls -l /dev/dri/                     # renderD128 … must exist
groups                              # must include `render` (or `video`)
sudo apt install vainfo ffmpeg      # Intel also: intel-media-va-driver-non-free
vainfo 2>&1 | grep -E 'VA-API version|H264.*VLD'
```

Expected: `VA-API version: 1.20` or newer, and `VAProfileH264Main :
VAEntrypointVLD` / `VAProfileH264High : VAEntrypointVLD` (Intel iHD, AMD
radeonsi). Paste the full `vainfo` output into the report.

## 1. Developer test on the device (needs a Rust toolchain)

```bash
cd native
cargo test -p platform-linux --all-features -- --ignored vaapi_decodes_the_golden_streams --nocapture
cargo test -p platform-linux --all-features golden -- --nocapture
cargo test -p platform-linux --all-features -- --ignored vaapi_encode_to_vaapi_decode_round_trip --nocapture
cargo test -p platform-linux --all-features -- --ignored vaapi_decode_1080p_within_4ms --nocapture
```

The round trip (L3's VA-API encoder → this decoder) must pass: every frame
decoded within coding error of the source, a delta fed first gives no
picture, and 640x360 → 320x240 on one decoder reports the new size.

**Acceptance — 1080p60 ≤ 4 ms/frame (Intel iGPU):** the timing test prints
`VA-API 1080p decode+read-back over 119 frames: mean X ms, p95 Y ms, max Z ms`.
**PASS if the test passes (mean ≤ 4.0 ms); FAIL otherwise** — report all three
numbers either way (AMD: report them; the 4 ms budget is set for Intel).

Expected: the first test prints `VA-API decode probe: VA-API on /dev/dri/renderD128 — …
(VA-API 1.2x; H.264 Constrained Baseline/Main/High)`, then for each H.264
stream `<name>: N frames match FFmpeg` (`nvenc-h264-main-640x360`,
`openh264-cb-320x240`, `x264-high-refs4-cqm-352x288`) and `resolution change
… on one decoder: ok`. Any "pixels differ from FFmpeg's" is a failure:
report the stream name and frame number — it pinpoints a parameter mistake
(frame 0 wrong: picture/IQ/slice buffers; later frames only: references).
The x264 stream exercises scaling matrices, weighted prediction, 4 references
and 4 slices; if only it fails, say so.

## 2. Run the app as viewer and read the probe

Connect from this machine to the Windows host, then:

```bash
grep -E 'hardware decoder|VA-API|NVDEC|openh264' ~/.local/state/sharectrl/app.log
```

* **24.04 Intel/AMD** — `hardware decoder: VA-API on /dev/dri/renderD128 — … H.264 …`,
  `VA-API decoder ready`, then at the first keyframe
  `VA-API decoder: H.264 Main (profile_idc 77, level 4.x) 1920x1080 (coded 1920x1088), N surfaces`.
* **22.04 (any GPU)** — `hardware decoder unavailable — VA-API: renderD128: libva 2.14 … hardware video stays off …`
  and `hardware H.264 decoder unavailable (no H264 decoder on this system) — trying Cisco OpenH264`.
  A picture must still appear (software decode).
* **No GPU / no libva** — `VA-API: libva.so.2 not loadable …` or `no /dev/dri …`, same fallback.
* **NVIDIA** — `hardware decoder: NVDEC on NVIDIA GeForce … (H264, HEVC)`.

Known limitation: the VA-API decoder learns the stream's profile and size
only at the first keyframe. If the driver cannot take them (e.g. a host
sending High to a driver listing only Main, or a size past its limit), every
frame fails with `decode error: unsupported input: … this GPU's VA-API driver
decodes only …` (or `… decodes up to WxH`) and there is **no** switch to
OpenH264 mid-session. Report the line if you see it.

## 2b. AV1 through NVDEC (Ampere-or-newer NVIDIA viewer only)

AV1 decode is implemented but **not advertised** until this passes
(`ADVERTISE_AV1_DECODE` in `native/crates/platform-linux/src/codec/mod.rs`).
On a viewer with an RTX 30xx/40xx (or newer) and a build with that constant
set to `true`, connect to a Windows host whose GPU encodes AV1:

1. The host log negotiates `AV1`; the viewer log shows
   `NVDEC decoder: AV1 1920x1080 …`; a correct picture appears.
2. Change the host's resolution mid-session: the picture continues at the
   new size (a second `NVDEC decoder: AV1 …` line).

Both yes → flip the constant to `true` for good (one-line change, noted on
the L4 card).

## 3. Picture check (viewer on this machine, host on Windows)

Yes/no for each:

1. A picture appears within ~2 s of connecting.
2. Colours right on a red/green/blue/white/black test card (no tint, blacks black).
3. No smearing or blocky trails while dragging a window (wrong references
   show up exactly like this).
4. Change the host's screen resolution mid-session: the picture continues at
   the new size (log: a second `VA-API decoder: H.264 …` line with the new size).
5. Pull the network cable for 2 s and reconnect it: the picture freezes, then
   recovers within a few seconds (`requesting keyframe` in the log) — it must
   not stay smeared. (An NVIDIA viewer behaves differently by design: NVDEC
   conceals, so it may show smeared blocks until the next keyframe.)
6. Decode cost: watch `top` — the app's CPU at 1080p60 should be well below
   one core. (The pass/fail budget is the timing test in step 1.)
