# L5 — Linux video surface + wgpu presenter: tester checklist

What this proves: the remote screen shows inside the app window on Linux (X11 and
Wayland), sharp at every scale, with the hover toolbar, mouse, keyboard, file drop and the
Settings dialog behaving like the Windows build. The headless tests already cover Xvfb
(`tests/x11_surface.rs`) and headless sway (`tests/wayland_surface.rs`) on a software GPU;
everything below needs a real desktop.

## Machines (one pass each)

| # | Session | How to get it |
|---|---|---|
| A | **GNOME 46 Wayland** (Ubuntu 24.04 default) | log in normally; `echo $XDG_SESSION_TYPE` = `wayland` |
| B | **KDE Plasma 6 Wayland** (Kubuntu 24.04+, Fedora KDE 40+) | log in to "Plasma (Wayland)" |
| C | **Sway** (any distro, real session on a GPU) | `sway` from a TTY |
| D | **X11 VM** (Ubuntu 22.04, "Ubuntu on Xorg" at the login gear; or Xfce) | VirtualBox/virt-manager VM is fine — it exercises the GL/software fallback |

Optional extras: an NVIDIA proprietary-driver machine (A or D), a touchscreen laptop.

## Before you start

* **Build:** a CI-built AppImage or .deb from `port/multi-os` that includes L5 **and** a
  decoder (L4 hardware or the D2 OpenH264 fallback switched on in Settings → Advanced).
* **Host:** the Windows build sharing its screen, with Notepad (10 pt text) and a
  full-screen Paint canvas showing clear left/right/top/bottom edges.
* **Log:** `~/.local/state/sharectrl/app.log`; keep `tail -f` running. Log lines quoted
  below start with `video surface:` or `presenter:`.

For every step write **pass / fail**; for a fail a screenshot plus the log lines around it.

## 1. The picture appears

1. Connect with control. Expected: the remote desktop fills the window below the title
   bar, upright, colours like on the PC (not washed out), black bars only where the
   aspect ratios differ; no web page showing through.
2. Log, in order: `video surface: X11 child window …` (D) or `video surface: Wayland
   subsurface created (InWindow, …)` (A–C); `presenter: Vulkan adapter "<your GPU>" …`
   (or `Gl` in the VM — note which); `presenter: first frame presented (W x H)`.
3. W×H equals the window's content size in **physical** pixels (at 200 % about twice the
   logical size). The `viewer: requesting WxH from host` line shows the same numbers.
4. Host text is crisp (compare with a screenshot taken on the PC).

## 2. Scaling (A, B; C with `output * scale 1.5`)

1. Set 125 % and 150 % (GNOME: Settings → Displays → Fractional Scaling on; KDE: Display
   Configuration). Reconnect. Log: `video surface: fractional scale 1.250` / `1.500`;
   `client_size` (first-frame W×H) = logical × scale.
2. Text stays crisp; check the **left and top edge of the video** for a 1-px seam or
   blur (the protocol leaves subsurface position rounding to the compositor).
3. Drag the window to a monitor with another scale: the picture re-sharpens within a
   second.

## 3. Hover toolbar

1. Move slowly to the very top edge of the video. The session toolbar appears over the
   top 40 (logical) px **the moment** the pointer is within ~2 physical px — the picture
   does not move or shrink.
2. Click a toolbar button: it reacts (the click goes to the toolbar, not the remote).
3. Move down: the bar stays until ~56 px from the top, then the video covers it again.
4. Flick up out of the window: the bar shows.

## 4. Mouse and keyboard

1. Move, left/right/middle click, double-click, drag a window on the host: lands where the
   pointer is, also near the black bars.
2. Wheel one notch = one notch on the host, both directions; touchpad two-finger scroll
   scrolls smoothly (horizontal too).
3. Type in Notepad: letters, digits, arrows, Home/End, Shift+arrows, AltGr characters
   (on a non-US layout the **physical** key is sent; the host's layout decides the
   character). Ctrl+C / Ctrl+V on the host work.
4. Hold Shift, Alt+Tab away (or click another app), release Shift there, come back:
   the host has **no** stuck Shift (type a letter: lower case).
5. Hold the left button on the video, drag out of the window and release: the host
   sees the release (no stuck drag).

## 5. Settings / modal

1. Open Settings from the toolbar. The video disappears **before** the dialog paints; the
   dialog's fields take typing (nothing reaches the host). Close it: the last picture is
   back at once even if the host screen is static.
2. Repeat 10 times quickly: no flicker of the page through the video, no stuck keys.

## 6. File drop

1. Drag a file from the file manager (Nautilus / Dolphin / Thunar) onto the video. The
   pointer shows "copy"; dropping sends the file and the host pastes it into the window
   under the drop point.
2. Drag onto the video **while Settings is open** (video hidden): the drop goes to the
   app page, not the session.
3. Drag text (not a file) onto the video: refused.

## 7. Resize, minimise, fallback

1. Resize the window (drag edge, maximise, tile): the video follows within a frame; the
   host's resolution request follows after ~0.5 s.
2. Minimise and restore: picture back, input works.
3. Fallback window (A or B): quit, start with `SHARECTRL_VIDEO_WINDOW=separate
   ./ShareCtrlScreen*.AppImage`. Log `using the separate window`; the remote screen opens in
   an undecorated window next to the app; input, keys and drops work there; Settings
   hides it.

## 8. GPU paths

1. Note the `presenter:` adapter line. With `WGPU_BACKEND=gl` set: still works (log
   `Gl`, possibly `only FIFO is available`).
2. NVIDIA proprietary: no black video, no frozen frame after hide/show.
3. Touchscreen: tap on the video — no crash, no GTK criticals in the terminal.

## Known limits (not failures)

* WSLg (Windows' Weston) does not hide the video with its parent (spike finding 1): use
  `SHARECTRL_VIDEO_WINDOW=separate` there.
* Keys are taken whenever the video is shown with control (not only after a click),
  like AnyDesk.
