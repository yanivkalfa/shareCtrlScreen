# L7 — Linux shortcut capture (viewer): tester checklist

What this verifies: on a Linux **viewer**, with Settings → "Capture shortcuts" on, Super,
Alt+Tab and Alt+Esc act on the **remote** while the session window is focused and the
remote screen is shown — and the local desktop gets its keyboard back the moment you
click elsewhere. Verified so far only on Xvfb (no window manager, keys typed through
XTEST); **every desktop below is unverified**.

Needs a second machine to connect to (any OS) so you can see what the remote receives:
open a text editor and a keyboard tester page (e.g. `https://w3c.github.io/uievents/tools/key-event-viewer.html`)
on the remote.

Log file: `~/.local/state/sharectrl/app.log`. Lines to look for:

```bash
grep -E 'shortcut capture' ~/.local/state/sharectrl/app.log
```

## 0. Machine facts

```bash
lsb_release -ds; echo "$XDG_SESSION_TYPE $XDG_CURRENT_DESKTOP"; echo "$WAYLAND_DISPLAY $DISPLAY"
```

Run each section on the desktop it names. Log in to the matching session from the login
screen's gear menu (GNOME "Ubuntu" vs "Ubuntu on Xorg"; Plasma "Plasma (Wayland)" vs
"Plasma (X11)").

## 1. Common steps (repeat on every desktop)

1. Settings → "Capture shortcuts" on. Connect to the remote, click into the remote screen.
2. Log must show `shortcut capture on (X11 keyboard grab while focused)` or
   `shortcut capture on (Wayland shortcuts inhibitor)`.
3. Press and release **Super** → the remote's start menu / overview opens; the local one
   does **not**.
4. Hold **Alt**, tap **Tab** twice, release Alt → the remote switches windows; the local
   desktop does not.
5. **Alt+Esc**, **Super+E** (Windows remote: Explorer) → act on the remote.
6. Type a sentence in the remote editor → every character arrives once, none doubled
   (doubling on Wayland would mean the hook forwards as well as GTK — a bug).
7. Hold **Alt**, then click a local window outside the session window → the remote key
   tester shows `AltLeft` **up** (no stuck Alt); local Alt+Tab works again at once.
8. Click back into the session window → Super goes to the remote again.
9. Open a dialog in the app's own toolbar (e.g. Settings) while connected: the video is
   hidden → you can type into the dialog normally (X11: the grab must be released).
   Close it → Super goes to the remote again. **Known (Wayland):** the inhibitor stays on
   while the dialog is open, so Super / Alt+Tab pressed then do nothing at all (they go to
   the web view, not the local desktop) — record it, it is a planned follow-up, not a fail.
10. Disconnect → log shows no error; local Super works.
11. Press a media key (volume, play/pause, brightness) while the session window is focused:
    **known** — on X11 it does nothing anywhere (the shared keymap has no such keys, and the
    grab holds the keyboard); on Wayland the local desktop handles it. Record, not a fail.

## 2. GNOME 46 (Ubuntu 24.04), Wayland

* First time in step 3 GNOME shows "ShareCtrlScreen wants to inhibit shortcuts" →
  **Allow**. Note whether the very first Super press already went to the remote.
* Repeat with **Deny** (reset under Settings → Apps → ShareCtrlScreen → "Inhibit system
  keyboard shortcuts" off): Super must open the local Activities, and the log must show
  `the desktop refused to let this window take its keyboard shortcuts`.
* GNOME's escape combo: **Super+Escape** restores local shortcuts; log shows
  `the desktop took its shortcuts back`.
* Known risk to report: whether Super alone still opens Activities on this GNOME version
  even while inhibited (plans/02 §4).

## 3. KDE Plasma 6, Wayland

* No prompt is expected. Steps 1–10.
* Report which combo KDE keeps for itself (escape), and whether Alt+Tab is inhibited.

## 4. Sway (wlroots)

* Steps 1–10. Sway's escape: by default none bound; check `bindsym --inhibited` in the
  config. Super-based sway bindings must not fire while focused.
* Run the ignored compositor test from a source checkout inside sway (needs Rust):
  the `install_matches_what_the_compositor_offers` test in `platform-linux` with
  `--ignored` → must pass.

## 4b. XWayland (any Wayland desktop, app forced onto X11)

* Start the app from a terminal with `GDK_BACKEND=x11 sharectrl` (AppImage: the same env
  var before the AppImage path), connect with capture on.
* Expected: `install` refuses — the log shows `shortcut capture is off: the app runs under
  XWayland, where the desktop keeps its shortcuts; start it without GDK_BACKEND=x11 …`,
  the UI shows the "unsupported here" hint, and Super / Alt+Tab act locally (nothing is
  grabbed). Typing into the remote still works through the normal path.

## 5. X11 VM (Ubuntu 22.04 "Ubuntu on Xorg", or Xfce / Openbox)

* Log shows `X11 keyboard grab while focused`. Steps 1–10.
* While the session window is focused, from a terminal on another VT or over ssh:
  `DISPLAY=:0 xdotool key super` → the log shows `keys from a virtual (XTEST) keyboard:
  shortcut capture paused`; the key is not lost (it is replayed to the app, which handles it
  like a typed key), and Super pressed on the real keyboard now acts **locally** until you
  click away and back. Real typing still reaches the remote through the normal path.
* Open a GNOME/Xfce menu that grabs the keyboard (e.g. right-click desktop menu left open
  on another monitor), then focus the session window → log may show
  `cannot take the keyboard: another program is holding the keyboard (AlreadyGrabbed)`;
  closing the menu and refocusing must recover.

## Report

For each desktop: pass/fail for steps 3–10, the `shortcut capture` log lines, and anything
the desktop kept for itself.
