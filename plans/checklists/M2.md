# M2 — VideoToolbox encoder: Mac tester checklist

What this verifies: the macOS hardware encoder (`native/crates/platform-macos`,
`vt_encoder.rs`). It needs no permission (no TCC prompt), but it does need a real hardware
video encoder, so it cannot be proven on Windows. On any Apple-silicon Mac this takes about
10 minutes.

Report back: the macOS version, the Mac model (Intel or Apple Silicon, chip name), and
**the full terminal output of every step**.

## 0. Setup (once)

1. macOS 13 Ventura or newer. An SSH session works too; no GUI is needed.
2. Xcode command-line tools (`xcode-select --install`) and Rust (`https://rustup.rs`).
3. Get the branch: `git clone … && cd shareCtrlScreen/native && git checkout task/M2`
   (or the branch the orchestrator names).
4. Build the tests once: `cargo test -p platform-macos --no-run`.

## 1. Unit tests (pure logic + factory)

`cargo test -p platform-macos --lib`

Expected: every test passes, including `avcc::*`, `vt_params::*`, `convert::*` and
`codecs::*`. The log line `VideoToolbox HEVC encoder ready … ` (or `no hardware HEVC
encoder (…)`) comes from the one-time HEVC probe.

## 2. In-crate hardware tests

`cargo test -p platform-macos --lib vt_encoder -- --ignored --nocapture --test-threads=1`

Expected: three tests pass.
* `native_frames_encode_zero_copy_and_start_with_an_idr` — an IOSurface `420v` buffer goes
  in with no copy; the first unit is a keyframe that starts `00 00 00 01 67…` (SPS first).
* `a_larger_capture_is_scaled_to_the_encode_size` — a 2560×1440 buffer into a 1280×720
  session. **If this one fails with `kVTParameterErr` or `kVTPixelTransferNotSupportedErr`,
  say so explicitly**: the design relies on VideoToolbox scaling a mismatched source.
* `forced_keyframes_and_live_bitrate_changes`.

Look for `VideoToolbox H264 encoder ready: … low-latency rate control` in the log. If it
says `standard rate control` instead, copy the `low-latency rate control refused (…)` line
above it. Lines `VideoToolbox: <key> not applied: …` are allowed, but copy them all.

## 3. Acceptance (plan task M2)

`cargo test --release -p platform-macos --test vt_encode -- --ignored --nocapture --test-threads=1`

1. `encodes_300_frames_first_idr_mean_under_8ms` — prints `N units, mean encode X ms`.
   Expected: passes; mean ≤ 8 ms on Apple silicon (copy the number either way).
2. `holds_the_bitrate_within_15_percent_over_5_seconds` — prints `… Mbit/s (R × target)`.
   Expected: R between 0.85 and 1.15, and the forced keyframe comes out.
3. `round_trip_through_the_platform_decoder_is_at_least_40_db` — prints the best luma PSNR.
   Expected: ≥ 40 dB. Before task M3 is merged the decoder is Cisco OpenH264, which is
   downloaded once from Cisco (the network is needed); after M3 it is VideoToolbox.

## 4. Intel Macs only

Repeat steps 2 and 3. Intel Macs often refuse low-latency rate control. The log must show
the fallback (`standard rate control`) and the tests must still pass. On an Intel Mac with
no hardware encoder at all, every test in step 2 fails with `no hardware H.264 encoder`:
report that, it is the expected result there (the app then uses OpenH264).

## 5. In the app (with M1 + M4 merged)

Share this Mac's screen to the Windows machine for 2 minutes, with typing, scrolling and a
video. Expected: a sharp picture with legible text and no periodic blur pulse (there are no
periodic keyframes). Put the Mac to sleep for 30 s while it is sharing, then wake it: the
log shows `VideoToolbox: encoder session rebuilt`, and the picture comes back within a few
seconds without reconnecting.
