# M3 — macOS VideoToolbox decoder: tester checklist

What this proves: the Mac viewer decodes the host's video with VideoToolbox
(hardware where the Mac has it), the picture reaches the Metal view without a
copy, resizing the window (which makes the host change resolution) keeps the
picture, and lost or damaged data recovers by itself.

## Before you start

* **Mac:** macOS 13 Ventura or later. Note the model (Intel / M1 / M2 / M3 or
  later) and the macOS version — AV1 decoding exists only on M3-generation
  chips and later.
* **Build:** a CI-built DMG from `port/multi-os` that contains M3 and M4.
* **Host:** a Windows PC running the current build, sharing its screen.
* **Log:** `tail -f ~/Library/Logs/ShareCtrlScreen/app.log` in Terminal.

For every step write **pass / fail**; for a fail add a screenshot
(Cmd+Shift+4) and the log lines around that time.

## 0. Automated tests (developer Mac or CI runner, no display needed)

1. `cd native && cargo test -p platform-macos -- decode:: codecs::` — all pass.
   This includes the 1080p → 720p → 1080p switch and the Metal import.
2. On a Mac with a hardware encoder:
   `cargo test -p platform-macos --lib decode:: -- --ignored --nocapture`.
   Expected: one line per codec, e.g. `H264: 47.3 dB`, every value ≥ 40, and
   `… frames match FFmpeg` for each golden stream (task T2, `decode::golden`).
   Without hardware the tests print `skipping:` and pass.
3. What CI covers (task T2, macOS job of `native-ci.yml`, not yet run — the branch is
   unpushed): step 2's two tests run there and skip with a `::warning` annotation when
   the hardware is missing; strict mode (`SCT_MAC_HW_TESTS_REQUIRED`, an opt-in repository
   variable) makes that a failure. Whether hosted macOS runners have the hardware is
   unproven until the first run. Its output is the golden check against FFmpeg's
   hashes: H.264 runs on whichever decoder VideoToolbox has (the log says which), and
   HEVC only where hardware decodes it. The rest of §1 still needs a Mac.

## 1. The decoder is VideoToolbox, in hardware

1. Connect from the Mac to the Windows host.
2. Expected in the log: `videotoolbox: <codec> stream format WxH (new session)`
   and `videotoolbox: <codec> decoder session ready (hardware)`. Note the codec
   (H264 / Hevc / Av1). `(software)` on a real Mac is a fail — report the model.
3. Expected: the `decoder session ready` line of step 2 appears within a few
   seconds of connecting, before the first picture. A line
   `hardware H.264 decoder unavailable … trying Cisco OpenH264` instead is a
   fail: VideoToolbox refused to open an H.264 decoder on this Mac and the
   viewer fell back to software — report the model, the macOS version and
   that line.

## 2. Picture

1. Expected: the remote desktop is sharp, colours as on the PC (not washed out,
   not too dark), no green or pink bands, no flicker.
2. Drag a window around on the host for 30 seconds. Expected: smooth, no
   blocky trails that stay on screen.

## 3. Resize = resolution change

1. Resize the Mac window from large to small and back, three times, pausing
   a second each time.
2. Expected: about a second after each resize the log shows
   `viewer: requesting WxH from host`, then `videotoolbox: … stream format WxH`
   with `(session kept)` or `(new session)`. The picture comes back sharp each
   time, at most a brief freeze; never a permanent black or frozen picture.

## 4. Recovery

1. On the host, play a fast-moving video full screen. On the Mac, switch
   Wi-Fi off for 3 seconds and on again.
2. Expected: the picture freezes or smears briefly, then recovers within a few
   seconds without reconnecting. The log may show `decode error: … a new
   keyframe is requested` and `viewer: no decodable frames — requesting keyframe`.
3. Close the Mac lid (or Apple menu → Sleep) during a session for 10 seconds,
   then wake it. Expected: the session either recovers on its own or ends with
   a message; if `kVTInvalidSessionErr` appears in the log, the next lines must
   show a new session being created.

## 5. Codec coverage (if the hardware allows)

* An M3-or-later Mac with a host that encodes AV1: the log in §1 says `Av1`.
  Repeat §2–§4.
* Any Apple silicon Mac with a host that encodes HEVC: the log says `Hevc`.
  Repeat §2–§4.
