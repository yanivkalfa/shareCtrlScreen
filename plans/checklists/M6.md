# M6 — macOS shortcut capture (event tap): tester checklist

What this proves: with "Capture system shortcuts" on, every Cmd shortcut except Cmd+Q
(M12; M6 had only Cmd+Tab, Cmd+\` and Cmd+Space) and Ctrl+arrows pressed in the session
window act on the remote computer instead of the Mac,
and the Mac gets them back the moment you click anywhere else. None of this can run on a
CI runner (the tap needs a GUI session and TCC grants); the decision logic itself is
covered by `crates/platform-macos/tests/shortcut_filter.rs` on every OS.

## Before you start

* **Mac:** macOS 13 or later. Note the model, macOS version, and the keyboard (built-in /
  external; does it have right-hand Cmd and Ctrl?).
* **Build:** a CI-built DMG from `port/multi-os` containing M4 (video view), M6, M11, and a
  decoder (M3 or D2). Install as in the M4 checklist.
* **Host:** a Windows PC running the current Windows build, with three or four apps open
  (Notepad, Explorer, a browser) so app switching is visible.
* **Log:** `tail -f ~/Library/Logs/ShareCtrlScreen/app.log` in Terminal.
* **Turn capture on:** quit the app, open
  `~/Library/Application Support/ShareCtrlScreen/config.json` and set
  `"captureShortcuts": true` (the Settings dialog has no toggle for it yet), then start
  the app again.

For each step write **pass / fail**; for a fail add a screenshot (Cmd+Shift+4 **after
clicking outside the session window** — with the video focused it now goes to the remote)
and the log lines around it.

## 1. Permissions

1. On a Mac where ShareCtrlScreen has no grants yet, press Connect.
   Expected: the permissions modal shows **Keyboard shortcuts** as not granted, and the
   notes say keyboard shortcuts need two switches (Input Monitoring and Accessibility).
2. Click the row's button. Expected: the Input Monitoring prompt; after granting it (and
   restarting the app if macOS asks), the row is **still** not granted and the next click
   asks for **Accessibility** (prompt first time, the Accessibility pane after).
3. Grant both. Expected: the row reads granted; the "two switches" note is gone.
4. Connect with control. Expected log line:
   `shortcut capture on: every Cmd shortcut except Cmd+Q, and Ctrl+arrows, go to the remote …`.
5. Disconnect, turn Accessibility **off** in System Settings, connect again.
   Expected log: `shortcut capture is off: ShareCtrlScreen does not have the Accessibility
   permission …`; the session still works; Cmd+Tab switches apps on the Mac.
   Turn Accessibility back on.

## 2. Capture while focused

Click once inside the remote picture first (that gives the video the keyboard).

Cmd reaches a Windows host as the **Windows key** (how Mac modifiers should map to the
host is an open owner decision; see the M6 card in `plans/05-TASKS.md`). So Cmd+Tab
arrives as **Win+Tab**, which opens Task View; it does not cycle apps or commit on
release the way the Mac switcher does. Steps 1–2 check that the chord *arrives*, not
that apps switch.

1. **Cmd+Tab**, then release both keys.
   Expected: **Task View** opens on the Windows host; the Mac's own switcher never
   appears. Close Task View on the remote with Esc.
2. **Cmd+Shift+Tab**: same as step 1 (Task View on the remote), nothing on the Mac.
3. **Cmd+Space**: Spotlight does **not** open on the Mac.
4. **Cmd+\`**: the Mac does not cycle its windows.
5. **Ctrl+←, Ctrl+→, Ctrl+↑, Ctrl+↓**: no Space switch, no Mission Control, no App
   Exposé on the Mac; on the remote (e.g. in Notepad) Ctrl+← / Ctrl+→ jump by word.
6. Hold **Ctrl+→** for two seconds: the remote cursor keeps jumping (auto-repeat), the Mac
   stays on its Space.
7. **Cmd+Q** while focused: the app **quits** (M12: Cmd+Q is the local escape hatch; before
   M12 it went to the remote). Start the app again and reconnect for the next steps.

## 3. Escapes (must always work)

1. Click another app's window (e.g. Finder) with the mouse, then press Cmd+Tab.
   Expected: the **Mac's** switcher appears at once — no delay, no second try needed.
2. Click the web toolbar above the video (hover the top edge), then Cmd+Tab.
   Expected: local switcher (the video no longer has the keyboard).
3. With the video focused, press **Cmd+Option+Esc**. Expected: the Mac's Force Quit window
   opens (never captured). Close it.
4. Cmd+Shift+4 with the video focused: **no** cross-hair on the Mac (M12 sends it to the
   remote, see §6). Click Finder, press Cmd+Shift+4: the Mac's cross-hair appears (Esc).
5. Start a Cmd+Tab with the video focused, keep Cmd held, and click Finder with the mouse;
   release Cmd. Expected: no key stays stuck on the remote — type in Notepad afterwards
   and check that letters are not turned into Win+letter shortcuts.

## 4. Cmd held while switching in

1. Focus Finder. Hold Cmd, press Tab until ShareCtrlScreen is selected, release Tab but
   **keep Cmd held**; click into the video still holding Cmd; press Tab again.
   Expected: **Task View** opens on the remote (Win+Tab — proof the hook sent Cmd's down
   itself; plain Tab would only move focus), and the Mac's switcher does not appear.
   Release Cmd, close Task View with Esc, then type in Notepad: letters arrive as
   letters (no modifier stuck on the remote).

## 5. Robustness (Terminal; developer machine with the repo checked out)

1. `cd native && cargo test -p platform-macos --lib -- --ignored probe` from a Terminal
   that has Accessibility. Expected: `probe_tap_answers_without_hanging` passes in well
   under a second. Repeat after turning Terminal's Accessibility off: still passes (the
   probe answers "no", it must not hang).
2. Secure Input: in a session with the video focused, open Terminal → **Secure Keyboard
   Entry** on. Expected log: `shortcut capture paused: Secure Input is active`; Cmd+Tab
   now acts on the Mac (macOS hides keys from every tap — expected). Turn it off: log
   `shortcut capture resumed`, capture works again without reconnecting.
3. Connect while Secure Keyboard Entry is already on. Expected log:
   `shortcut capture on: …` followed by `shortcut capture paused: Secure Input is active …`;
   the connection works, Cmd+Tab is local. Turn Secure Keyboard Entry off: within ~1 s the
   log says `shortcut capture resumed`, and Cmd+Tab goes to the remote **without
   reconnecting**.
4. Accessibility revoked mid-session: with a session running and capture on, turn
   ShareCtrlScreen off under Accessibility. Expected within ~1 s: log
   `shortcut capture stopped: the Accessibility permission was turned off …`; the Mac's
   keyboard and mouse keep working normally (no freeze); Cmd+Tab is local. If input
   **does** freeze, report it with the time it took to recover (or that a restart was
   needed): removing the tap is all an app can do, and this step is how we learn whether
   it suffices.
5. Disconnect. Expected log: `shortcut capture off`. Cmd+Tab is local afterwards.

## 6. Every Cmd shortcut (M12)

Host: an Ubuntu (GNOME) or Windows PC. "Translate modifiers for the remote OS" in
Settings → Advanced decides how Cmd arrives: **on** (default) Cmd = Ctrl on the host,
**off** Cmd = the Win/Super key. Run 1–6 with it on, then 1, 3 and 4 again with it off.
Click into the remote picture first.

| Step | Press on the Mac | Expected (translation on) | Expected (off) |
|---|---|---|---|
| 1 | **Cmd+C** on selected text in a host editor, then **Cmd+V** | text copied and pasted on the host (Ctrl+C / Ctrl+V); the Mac's own clipboard and Edit menu do nothing | Super+C / Super+V (GNOME: usually nothing; Windows: Win+V opens clipboard history) |
| 2 | **Cmd+Enter** in a host app that has a Ctrl+Enter action (e.g. a browser address bar, or a chat box) | Ctrl+Enter acts on the host | Super+Enter |
| 3 | **Cmd+Shift+4** | no cross-hair on the Mac; the host gets Ctrl+Shift+4 | Super+Shift+4 |
| 4 | **Cmd+Option+D** | the Mac Dock does **not** hide/show; the host gets Ctrl+Alt+D (GNOME: may show the desktop) | Super+Alt+D |
| 5 | **Cmd+W**, **Cmd+H**, **Cmd+M**, **Cmd+,** | nothing happens to the ShareCtrlScreen window; the host gets the Ctrl chords (Ctrl+W closes a host tab) | — |
| 6 | **Cmd+Q** | the viewer **quits** on the Mac (the escape hatch); the host does not get Ctrl+Q | same |
| 7 | Start Cmd+C, keep Cmd held, click the Mac desktop, release | Cmd+Tab right after is the **Mac's** switcher; type on the host afterwards: letters are letters (no Ctrl/Super stuck) | same |
| 8 | **Cmd+Option+Esc** with the video focused | the Mac's Force Quit window (never taken) | same |
| 9 | **Cmd+Ctrl+Q** with the video focused | the Mac locks (never taken); log in again, nothing stuck on the host | same |
| 10 | Shift and Option pressed fast together with Cmd: **Cmd+Shift+Z** quickly followed by **Cmd+Z** (Shift released in between) in a host editor | redo, then undo (never two redos) | — |

With the debug log (`app.log`), each taken chord produces no Mac-side line; a
`… stays with macOS` line appears for steps 8–9 (if macOS delivered them to the tap at all).
Steps 8–9 must also not reach the host (no Ctrl+Q / Esc there): the video view's key
monitor lets them through to macOS too. Cmd+Q with capture **off** is checked in
checklists/M4.md §7 step 3.

Keyboard layouts: "Q" is the key that types `q` on the active layout (AZERTY: the key in
the US "A" position). On a layout that switches to QWERTY while Cmd is held ("Dvorak –
QWERTY ⌘"), the tap and the view read the character through different APIs and may
disagree about which key is Q: then Cmd+Q may go to the remote, or Cmd plus the other key
may quit. Nothing gets stuck either way; if you use such a layout, try Cmd+Q and report
which physical key quit.

## 7. Toolbar reveal (video view; owner report "the top edge does nothing")

Not full screen first, then in native full screen (green button). `app.log` at debug.

1. Connect; move the pointer over the picture. Expected log once:
   `video view: pointer events arrive (first move at y=…)`. **If this line never appears**,
   mouse-moved events do not reach the view (report it: it is the root cause).
2. Move slowly to the very top edge of the picture. Expected: the session bar (Disconnect /
   Refresh / ⚙) appears; log `toolbar reveal: Reveal at y=…px … view frame …, layer frame …`.
   If the line appears but nothing changes on screen, report the two frames (they should
   both be 40 pt shorter than the window's content).
   With the bar shown, check the picture: it must fill **exactly** the area below the bar —
   no black or empty gap between bar and picture, no strip of picture above or over the
   bar, not shifted sideways, the bottom edge still at the window's bottom. Screenshot it
   (after clicking outside the window, Cmd+Shift+4) if any of that is off.
   **If the "pointer events arrive" line is logged but no `Reveal` line appears** when the
   pointer is at the very top: move very slowly up to the top edge, then report the `y=`
   of the first-move line from a fresh show (disconnect/reconnect and make the first move
   right at the top). A value well above 0 there means the pointer's height is mapped
   wrongly, not that nothing happened.
3. Move down into the picture past about 56 pt below the top: the bar hides; log
   `toolbar reveal: Hide …`. The picture returns to full size: it fills the whole content
   area again (top edge at the top), nothing left shifted or cropped.
4. Flick the pointer quickly out through the top edge (into the title bar): the bar appears.
5. Click **Refresh** and **Disconnect** on the bar: both work.
6. Full screen: push to the top edge; the macOS menu bar slides down over the window, and
   the session bar is revealed underneath it. Move down out of the menu bar: the session
   bar stays visible (it hides only about 56 pt below the menu bar's lower edge); move up
   onto it and click ⚙: Settings opens.
7. If a log line `video view: layer frame … did not follow the view frame …; set it`
   appears, report it (AppKit did not resize our layer by itself, and the view set it).
   Then repeat the picture check of step 2 (bar shown: picture exactly below it, no gap,
   no offset) and of step 3 (bar hidden: full size) with particular care: that line means
   our own layer placement is in use, and a wrong placement shows as exactly such a gap or
   offset, on macOS only.

Report back: macOS version, chip, keyboard, and for any fail the step number, what
happened on the Mac and on the remote, and the log lines.
