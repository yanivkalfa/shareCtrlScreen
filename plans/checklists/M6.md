# M6 — macOS shortcut capture (event tap): tester checklist

What this proves: with "Capture system shortcuts" on, Cmd+Tab, Cmd+\`, Cmd+Space and
Ctrl+arrows pressed in the session window act on the remote computer instead of the Mac,
and the Mac gets them back the moment you click anywhere else. None of this can run on a
CI runner (the tap needs a GUI session and TCC grants); the decision logic itself is
covered by `crates/platform-macos/tests/shortcut_filter.rs` on every OS.

## Before you start

* **Mac:** macOS 13 or later. Note the model, macOS version, and the keyboard (built-in /
  external; does it have right-hand Cmd and Ctrl?).
* **Build:** a CI-built DMG from `port/multi-os` containing M4 (video view), M6, M11, and a
  decoder (M3 or D2). Install as in the M4 checklist.
* **Host:** a Windows PC running the current Windows build, with three or four apps open
  (Notepad, Explorer, a browser) so app switching is visible.
* **Log:** `tail -f ~/Library/Logs/ShareCtrlScreen/app.log` in Terminal.
* **Turn capture on:** quit the app, open
  `~/Library/Application Support/ShareCtrlScreen/config.json` and set
  `"captureShortcuts": true` (the Settings dialog has no toggle for it yet), then start
  the app again.

For each step write **pass / fail**; for a fail add a screenshot (Cmd+Shift+4, which is
never captured) and the log lines around it.

## 1. Permissions

1. On a Mac where ShareCtrlScreen has no grants yet, press Connect.
   Expected: the permissions modal shows **Keyboard shortcuts** as not granted, and the
   notes say keyboard shortcuts need two switches (Input Monitoring and Accessibility).
2. Click the row's button. Expected: the Input Monitoring prompt; after granting it (and
   restarting the app if macOS asks), the row is **still** not granted and the next click
   asks for **Accessibility** (prompt first time, the Accessibility pane after).
3. Grant both. Expected: the row reads granted; the "two switches" note is gone.
4. Connect with control. Expected log line:
   `shortcut capture on: Cmd+Tab, Cmd+`, Cmd+Space and Ctrl+arrows go to the remote …`.
5. Disconnect, turn Accessibility **off** in System Settings, connect again.
   Expected log: `shortcut capture is off: ShareCtrlScreen does not have the Accessibility
   permission …`; the session still works; Cmd+Tab switches apps on the Mac.
   Turn Accessibility back on.

## 2. Capture while focused

Click once inside the remote picture first (that gives the video the keyboard).

Cmd reaches a Windows host as the **Windows key** (how Mac modifiers should map to the
host is an open owner decision; see the M6 card in `plans/05-TASKS.md`). So Cmd+Tab
arrives as **Win+Tab**, which opens Task View; it does not cycle apps or commit on
release the way the Mac switcher does. Steps 1–2 check that the chord *arrives*, not
that apps switch.

1. **Cmd+Tab**, then release both keys.
   Expected: **Task View** opens on the Windows host; the Mac's own switcher never
   appears. Close Task View on the remote with Esc.
2. **Cmd+Shift+Tab**: same as step 1 (Task View on the remote), nothing on the Mac.
3. **Cmd+Space**: Spotlight does **not** open on the Mac.
4. **Cmd+\`**: the Mac does not cycle its windows.
5. **Ctrl+←, Ctrl+→, Ctrl+↑, Ctrl+↓**: no Space switch, no Mission Control, no App
   Exposé on the Mac; on the remote (e.g. in Notepad) Ctrl+← / Ctrl+→ jump by word.
6. Hold **Ctrl+→** for two seconds: the remote cursor keeps jumping (auto-repeat), the Mac
   stays on its Space.
7. **Cmd+Q** while focused: the app does **not** quit (the video view sends it to the
   remote, which is unchanged by M6).

## 3. Escapes (must always work)

1. Click another app's window (e.g. Finder) with the mouse, then press Cmd+Tab.
   Expected: the **Mac's** switcher appears at once — no delay, no second try needed.
2. Click the web toolbar above the video (hover the top edge), then Cmd+Tab.
   Expected: local switcher (the video no longer has the keyboard).
3. With the video focused, press **Cmd+Option+Esc**. Expected: the Mac's Force Quit window
   opens (never captured). Close it.
4. Cmd+Shift+4 with the video focused: the Mac's screenshot cross-hair appears.
5. Start a Cmd+Tab with the video focused, keep Cmd held, and click Finder with the mouse;
   release Cmd. Expected: no key stays stuck on the remote — type in Notepad afterwards
   and check that letters are not turned into Win+letter shortcuts.

## 4. Cmd held while switching in

1. Focus Finder. Hold Cmd, press Tab until ShareCtrlScreen is selected, release Tab but
   **keep Cmd held**; click into the video still holding Cmd; press Tab again.
   Expected: **Task View** opens on the remote (Win+Tab — proof the hook sent Cmd's down
   itself; plain Tab would only move focus), and the Mac's switcher does not appear.
   Release Cmd, close Task View with Esc, then type in Notepad: letters arrive as
   letters (no modifier stuck on the remote).

## 5. Robustness (Terminal; developer machine with the repo checked out)

1. `cd native && cargo test -p platform-macos --lib -- --ignored probe` from a Terminal
   that has Accessibility. Expected: `probe_tap_answers_without_hanging` passes in well
   under a second. Repeat after turning Terminal's Accessibility off: still passes (the
   probe answers "no", it must not hang).
2. Secure Input: in a session with the video focused, open Terminal → **Secure Keyboard
   Entry** on. Expected log: `shortcut capture paused: Secure Input is active`; Cmd+Tab
   now acts on the Mac (macOS hides keys from every tap — expected). Turn it off: log
   `shortcut capture resumed`, capture works again without reconnecting.
3. Connect while Secure Keyboard Entry is already on. Expected log:
   `shortcut capture on: …` followed by `shortcut capture paused: Secure Input is active …`;
   the connection works, Cmd+Tab is local. Turn Secure Keyboard Entry off: within ~1 s the
   log says `shortcut capture resumed`, and Cmd+Tab goes to the remote **without
   reconnecting**.
4. Accessibility revoked mid-session: with a session running and capture on, turn
   ShareCtrlScreen off under Accessibility. Expected within ~1 s: log
   `shortcut capture stopped: the Accessibility permission was turned off …`; the Mac's
   keyboard and mouse keep working normally (no freeze); Cmd+Tab is local. If input
   **does** freeze, report it with the time it took to recover (or that a restart was
   needed): removing the tap is all an app can do, and this step is how we learn whether
   it suffices.
5. Disconnect. Expected log: `shortcut capture off`. Cmd+Tab is local afterwards.

Report back: macOS version, chip, keyboard, and for any fail the step number, what
happened on the Mac and on the remote, and the log lines.
