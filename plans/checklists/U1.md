# U1 — In-app updater: check, download, install, restart (tester checklist)

Needs: a **published, updater-enabled** GitHub release to update FROM, and a newer
one to update TO. The mechanism ships in one release; proving a real update needs a
**second** updater-enabled release with a higher version. So the full pass is:

1. The orchestrator has run `native/scripts/updater-make-key.sh`, created the repo
   secrets `TAURI_SIGNING_PRIVATE_KEY` + `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`, and
   pasted the printed **public key** into `native/app/tauri.conf.json`
   (`plugins.updater.pubkey`, replacing the `REPLACE_WITH_…` placeholder).
2. Cut release **A** (e.g. `v2.1.6`) from a tag — this ships the updater. Confirm the
   release carries `latest.json` and the `.sig` files (see CI steps below).
3. Bump the version, cut release **B** (e.g. `v2.1.7`). `latest.json` on "latest" now
   points at B.
4. Install **A** on a test machine and run the steps below; it must find and install B.

The app writes `app.log` in `%APPDATA%\ShareCtrlScreen` (Windows). SmartScreen warns on
first run of an unsigned build: **More info → Run anyway**.

## Proven by CI (no device)

| Check | Where |
|---|---|
| Rust compiles with the plugins; `restart_plan` unit tests; clippy/fmt/tests; cargo-deny licences | `native-ci.yml` build-test + license-gate |
| A signed release emits a `.sig` for each updater target and a schema-valid `latest.json` with a `windows-x86_64` entry | `release.yml` checksums job (`updater-latest-json.sh` + `updater-check-latest-json.py`); exercised by a dry run (Actions → Release → Run workflow) |

## Device steps (from installed release A, with release B published)

| Step | Action | Must see |
|---|---|---|
| 1 | Open Settings → **Updates**. Current version reads A | the version line shows A; "Check for updates" present |
| 2 | Click **Check for updates** | within a few seconds: "Update available: &lt;B&gt;" with the release notes and an **Update & restart** button |
| 3 | (startup check) Fully quit and relaunch A | a toast "Update available: &lt;B&gt; — open Settings to install" appears without blocking the window or hosting |
| 4 | **Portable / non-service Windows install:** click **Update & restart** | a progress line; the app closes; the NSIS installer runs silently (passive); the app reopens on version **B**, ready to connect |
| 5 | **Service install (installer build):** `sc query ShareCtrlScreenHost` is RUNNING before; click **Update & restart** | the app closes; `sc query` shows the service stopped then RUNNING again (its PID changed); exactly **one** `sharectrl.exe` host comes back (no duplicate); version is **B**; `app.log` says it was started by the service |
| 6 | Mid-session update: start a session (be the viewer or host), open Settings → Updates | the button reads **End session & update** and an inline warning says updating ends the session |
| 7 | Click **End session & update** during the live session | the session ends cleanly (the peer is told, not just dropped); the update proceeds; the app returns on **B** |
| 8 | After the update, reconnect to a peer | works normally on **B** |
| 9 | **macOS:** from an installed A (DMG), check + Update & restart | the app replaces itself in place and relaunches on **B**; Screen Recording / Accessibility are still granted (certificate-signed archive) |
| 10 | **Linux (AppImage):** from an installed A, check + Update & restart | the AppImage updates and relaunches on **B** |
| 11 | **.deb / .rpm users:** (if tested) | the UI does NOT silently self-update these; they are told to download from Releases |

Report back: OS + version; whether the service install came back as exactly one host
(critical — a duplicate or a host left down is a fail); whether a live session ended
cleanly; and whether macOS kept its permissions across the update. Note any case where
the app self-relaunched on a service install (it must not) or failed to reconnect.

## U2 — Settings/Updates reachable while hosting (manual)

Added by U2: a Settings gear (`btn-host-settings`, ⚙) on the host sharing
screen (`screen-host`), mirroring the viewer gear. No Rust changed.

| Step | Action | Must see |
|---|---|---|
| 1 | Host a session (be the shared/controlled machine) so the "Sharing screen with …" screen is up | a ⚙ gear sits in the header, right of the "connected" status |
| 2 | Click the gear | the Settings modal opens **above** everything; screen sharing does not stop and the session stays live (the peer is not dropped) |
| 3 | Scroll to **Updates** | the current version, "Check for updates", and (if an update exists) "Update & restart" are all present and usable |
| 4 | Click **Check for updates** | it runs and reports (same as from the home/viewer gear) |
| 5 | If an update is offered mid-session | the button reads **End session & update** with the U1 inline warning (updater logic unchanged) |
| 6 | Close Settings (Cancel/Save) | the modal closes and the host screen is intact; on the host the native video restore is a no-op (no receive surface), so nothing flickers |

Note: `set_video_visible` only affects the viewer's receive surface; on the
host it is a no-op, so there is no video to fail to restore. The follow-up
"controller triggers the host's update remotely" is NOT part of U2.
