# V1 — Host follows the bandwidth estimate down (smooth video, sharp text)

Device-only acceptance. The lane proves the logic (the encoder target tracks the
BWE down below the old floor and back up, the resolution ladder is monotonic +
hysteretic, no unpaced keyframe path remains) over the loopback harness, which has
no real congestion — so the *feel* on a genuinely constrained link, and the
on-screen resolution drop, are proven here on real hardware.

Needs a HOST and a VIEWER on different networks, and a way to constrain the link
between them (a relay/TURN path, a phone-tethered uplink, or a shaper that caps the
host's egress to ~400-700 kbps). Run it on a **Windows host** and again on a
**Linux host** (both report the stutter today; the Linux host is software-encoding
over a relay, the Windows host once the SYSTEM service launches it — see W8).

Host log: `%APPDATA%\ShareCtrlScreen\app.log` (Windows) /
`~/.local/share/ShareCtrlScreen/app.log` (Linux). The relevant lines are the 5-second
`video/tx: … applied {N} kbps, bwe {M} kbps` telemetry and the `bwe: link … →
encoder …` / `host: re-encoding at WxH` lines.

## 1. Quick one-knob pre-check (owner can eyeball first)
1. Start a session over the constrained link, controlled from the viewer.
2. In the host log, watch the `video/tx` line as the link congests:
   - [ ] `applied` TRACKS `bwe` downward — when `bwe` reads ~300-600 kbps, `applied`
     follows to ~500 kbps (the new floor), **not** pinned at ~2500 as before.
   - [ ] It does not sit at 2500 while `bwe` is far below it (the old regression).

## 2. The estimate settles instead of oscillating (deliverable 1 + 3 + 4)
- [ ] After a few seconds `bwe` SETTLES around the link's real capacity rather than
  swinging 65 ↔ 3700 kbps. No sustained oscillation.
- [ ] `host: re-encoding at WxH` appears a small number of times as the link changes,
  then stops (the ladder is not flapping every second).
- [ ] The keyframe log (`keyframes/5s: …`) shows at most ~1 requested IDR/second; no
  burst of IDRs coinciding with the estimate collapsing.

## 3. Smooth, and text stays sharp (acceptance)
- [ ] Mouse movement and typing feel responsive — no "mouse stays behind", no lag
  building up over the session.
- [ ] A moving window / scrolling text is fluid, not a slideshow. Frame rate looks
  steady (it should read ~30 fps in `video/tx` on a link that carries the smallest
  ladder step; only a sub-500 kbps link drops fps, and even then it stays ≥ 4 and
  keeps updating — not frozen).
- [ ] The picture is a SHARP SMALLER image, not full-resolution mush: text is legible.
  The host log shows a reduced `re-encoding at WxH` (e.g. 0.5 or 0.33 of full) while
  constrained — degradation is spent on resolution, not sharpness.

## 4. Recovery when the link frees up (deliverable 1 + 2)
With the session live, remove the constraint (stop the shaper / move to a fast link):
- [ ] `bwe` climbs back up and `applied` tracks it up toward 8 Mbps (not stuck low —
  the dipped estimate recovers).
- [ ] `host: re-encoding at WxH` steps the resolution back UP to full size.
- [ ] The picture returns to full resolution and stays smooth throughout.

## 5. Both hosts
- [ ] Section 1-4 pass with a **Windows** host.
- [ ] Section 1-4 pass with a **Linux** host (software encode over a relay).

Pass = sections 1-4 green on both a Windows and a Linux host. If `applied` still
pins high while `bwe` is low (section 1 fails), the encoder is not following the
estimate down — capture the full `app.log` and report before closing.
