# V2 — Remove the resolution ladder; sharp, STEADY full-resolution video

Device-only acceptance. The lane proves the LOGIC (the encoder bitrate tracks the
BWE down to the floor and back up, the encode size stays full regardless of the
link, no unpaced keyframe path, no source pacer) over the loopback harness, which
has no real congestion and a mock encoder that does not resample. So the *feel* on
a genuinely constrained link — and critically that the picture no longer
constantly softens and re-sharpens — is proven here on real hardware.

Context: V1 (2.1.8) added a bandwidth-driven `RESOLUTION_LADDER` that scaled the
ENCODE RESOLUTION up/down from the estimate. On a noisy or even good link it scaled
down and oscillated between steps, so the image "ever blurred and focused on things
that don't change" (owner). V2 removes the ladder: the encoder ALWAYS encodes at
the full viewer-fit resolution and absorbs a constrained link purely in the
BITRATE (a softer but STEADY picture). V1's proven-smooth core (bitrate follows BWE
down, str0m paces egress, no keyframe-pacer-bypass) is kept.

Needs a HOST and a VIEWER. Run on a **Windows host** first (the owner reports the
blur there too), then a **Linux host** (software encode over a relay). A way to
constrain the link helps section 3-4 but is not needed for the core section 1
steadiness check.

Host log: `%APPDATA%\ShareCtrlScreen\app.log` (Windows) /
`~/.local/share/ShareCtrlScreen/app.log` (Linux). The relevant lines are the
5-second `video/tx: … applied {N} kbps, bwe {M} kbps` telemetry, the `bwe: link …
→ encoder …` lines, and `host: re-encoding at WxH` (which must now appear ONLY on a
viewer window resize, never from the link changing).

## 1. Sharp and STEADY on a good link (the core acceptance — the owner's complaint)
With a normal/good link and a still or lightly-changing screen:
- [ ] The picture is SHARP and stays sharp — no constant soften-then-sharpen pulse,
  no "breathing" blur on static content.
- [ ] `host: re-encoding at WxH` does **not** appear while the window is left alone.
  It appears only when you actually resize the viewer window (and then once, settling
  at the new size). It must NOT fire from bandwidth-estimate movement.
- [ ] The encode size in the log stays at the full viewer-fit resolution the whole
  session (no 0.75/0.5/0.33 scaling lines).

## 2. Bitrate still follows the link (deliverable 2 kept)
- [ ] In `video/tx`, `applied` TRACKS `bwe`: on a good link it rises toward ~8000 kbps;
  it is not pinned low.
- [ ] `applied` never pins at the old 2500 kbps while `bwe` is far below it.

## 3. Steady and smooth when the link is constrained (acceptance)
Constrain the link (shaper to ~400-700 kbps, or a phone-tethered uplink):
- [ ] The picture gets SOFTER but stays STEADY — it does not flap between sharp and
  blurry. Degradation is smooth, not oscillating.
- [ ] The resolution stays FULL (no `re-encoding at WxH` shrink lines) — only the
  bitrate drops (`applied` follows `bwe` down toward ~500 kbps).
- [ ] Mouse movement and typing stay responsive — no "mouse stays behind", no garble
  or overshoot, no lag building over the session. Frame rate stays ~30 fps.
- [ ] `bwe` settles around the link's real capacity rather than swinging 65 ↔ 3700.
- [ ] The keyframe log (`keyframes/5s: …`) shows at most ~1 requested IDR/second; no
  IDR burst coinciding with an estimate collapse.

## 4. Recovery when the link frees up
With the session live, remove the constraint:
- [ ] `bwe` climbs back and `applied` tracks it up toward ~8000 kbps (not stuck low).
- [ ] The picture re-sharpens once and STAYS sharp — it does not resume pulsing.
- [ ] No `re-encoding` size change happens on recovery (resolution was never changed).

## 5. Both hosts
- [ ] Sections 1-4 pass with a **Windows** host.
- [ ] Sections 1-4 pass with a **Linux** host (software encode over a relay).

Pass = sections 1-4 green on both a Windows and a Linux host, with section 1
(steady, non-pulsing sharpness) being the specific regression this fixes. If the
picture still pulses blurry/sharp on a steady screen, capture the full `app.log`
(look for unexpected `re-encoding at WxH` lines) and report before closing.
