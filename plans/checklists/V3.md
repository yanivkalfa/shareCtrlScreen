# V3 — The video quality PULSES (blurry→sharp→blurry); make it STEADY

Device-only acceptance. The lane proves the LOGIC — the pure `tuning::RateFilter`
(noise in → steady out; a sustained step is followed) and, over the loopback
harness, that the APPLIED encoder target stays steady while the injected estimate
oscillates and still follows a sustained trend. But the loopback has no real GCC
and a mock encoder, so the *feel* on a real noisy link — that the picture no longer
pulses blurry→sharp→blurry on a steady screen, and that encoder-initiated keyframes
drop — is proven here on real hardware, against the owner's own live host log.

Context: after V2 removed the resolution ladder the full-res picture STILL pulsed.
The owner's LIVE host log (2026-11-03) showed GCC's estimate swinging
`4574→3000→1432→692→4130→500` kbps within ~2 min on a capable link, and the encoder
`applied` bitrate following it 1:1 (V2's 15% hysteresis was far smaller than the
swings). So the quality pulsed (sharp ~4 Mbps, blocky ~500–900 kbps), and the
frequent reconfigs drove 1–4 encoder-initiated IDRs/5s despite GOP 600 — a feedback
loop that destabilised GCC further. V3 smooths the applied target (light EMA +
asymmetric sustained-window gate) so it moves only on a SUSTAINED trend, keeping V2
full resolution and the 500 k / 8 M floor/ceiling.

Needs a HOST and a VIEWER. Run on a **Windows host** first (the owner's machine,
where the live log came from), then a **Linux host** (software encode over a relay).

Host log: `%APPDATA%\ShareCtrlScreen\app.log` (Windows) /
`~/.local/share/ShareCtrlScreen/app.log` (Linux). The relevant lines are the
5-second `video/tx: … applied {N} kbps, bwe {M} kbps` telemetry, the `bwe: link …
→ encoder … (smoothed)` lines (these should now be RARE), and `keyframes/5s: …`.

## 1. STEADY on a stable-but-noisy link (the core acceptance — the owner's complaint)
With a normal/good link and a still or lightly-changing screen, over ≥2 minutes:
- [ ] The picture is SHARP and STAYS sharp — no blurry→sharp→blurry pulse every few
  seconds on static content.
- [ ] In `video/tx`, `applied` stays roughly STEADY even while `bwe` wobbles. It does
  NOT pulse 500 ↔ 4000 kbps tracking every `bwe` swing (the exact V2 regression).
- [ ] `bwe: link … → encoder … (smoothed)` lines are RARE — a handful over the
  session, not one every few seconds.

## 2. Encoder-initiated keyframes drop (deliverable 2)
- [ ] `keyframes/5s: … encoder-initiated …` is near zero on a steady screen — not the
  1–4/5s the owner's log showed. (Requested IDRs on connect/PLI/resize are fine.)
- [ ] No IDR burst coinciding with an estimate wobble (the reconfig→keyframe loop is
  broken because the bitrate rarely changes now).

## 3. Still follows a REAL sustained change (not over-damped — the V1 risk)
Constrain the link for a sustained period (shaper to ~700 kbps, or a tethered uplink
held down for >10 s):
- [ ] Within a few seconds `applied` comes DOWN toward the constrained capacity (it
  does not stay pinned high and overshoot — no "mouse stays behind", no garble).
- [ ] A brief (~1 s) dip on an otherwise good link does NOT drop `applied` — only a
  SUSTAINED drop does.
- [ ] The resolution stays FULL throughout (no `host: re-encoding at WxH` shrink lines
  from the link — V2's no-ladder behaviour is intact).

## 4. Recovery when the link frees up
With the session live, remove the constraint and hold it open:
- [ ] `applied` climbs back toward ~8000 kbps over a couple of seconds (smoothed, not a
  snap), and the picture re-sharpens once and STAYS sharp — it does not resume pulsing.
- [ ] No `re-encoding` size change on recovery (resolution was never changed).

## 5. Both hosts
- [ ] Sections 1-4 pass with a **Windows** host (the owner's machine — compare against
  the pre-fix log's 500↔4000 `applied` swings).
- [ ] Sections 1-4 pass with a **Linux** host (software encode over a relay).

Pass = sections 1-4 green on both a Windows and a Linux host, with section 1 (steady,
non-pulsing `applied` / sharpness on a noisy link) being the specific regression this
fixes. If `applied` still pulses on a stable link, capture the full `app.log`
(the `video/tx` applied/bwe series and the `(smoothed)` lines) and report before
closing — the EMA τ (1.5 s) or the hold windows (drop 3.0 s / raise 2.0 s) may need
tuning against the new log.
