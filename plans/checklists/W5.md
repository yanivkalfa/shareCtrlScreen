# W5 — UIAccess for the Windows host (Alt+Tab / Windows-key passthrough)

Device-only. The UIAccess token call does something only when the host is launched by the
SYSTEM service (route (a)); CI cannot exercise it. Two Windows machines on different
networks: **B** the viewer (controls), **H** the host (shared and controlled). On the viewer,
turn on ⚙ Settings → "Capture keyboard shortcuts" and connect to H with control.

What "works" means below: from B, **Alt+Tab** switches windows on H (hold Alt, tap Tab,
release — the task switcher appears on H and lands on another window), and the **Windows
key** opens the Start menu on H. After releasing, nothing is stuck on H (no ghost Alt, no
Start menu left open, typing is normal).

The running host logs one line near the top of `app.log`
(`%APPDATA%\ShareCtrlScreen\app.log`): `UIAccess: granted` or
`UIAccess: not granted — <reason>`. That line is the readout for the host instance the
service actually started — it is the authoritative "granted" check in §1.

`sharectrl.exe --print-uiaccess` is different: it reports the status of **that one
invocation** and exits 0 (granted) / 1 (not). Under route (a) the UIAccess flag lives only on
the process the service launches, so a `sharectrl.exe` you run by hand is a fresh non-service
process and will always print `not granted — the host was not started by the service` (exit
1), even on a perfectly working service host. It is a self-check for the invocation, not a
readout of the running service host. (It becomes a positive self-check only under the signed
route, W6.) Run it from a terminal that captures the output of a GUI exe, e.g.
`cmd /c "sharectrl.exe --print-uiaccess" & echo %errorlevel%`.

## 1. Service mode — the main case (should grant)
Install H with the W4 installer (so `sharectrl-service.exe` sits next to `sharectrl.exe` and
the service `ShareCtrlScreenHost` is RUNNING). The service launches the host.
1. On H, open `app.log`. The startup line of the service-started host says
   **`UIAccess: granted`**. (This is the authoritative granted check — not
   `--print-uiaccess`, which is a fresh non-service process and correctly reports `not
   granted` even here.)
2. `sharectrl-service.log` (next to the service exe, under Program Files) has a line
   **`launched engine pid=… in session … with UIAccess`**.
3. From B: **Alt+Tab** switches windows on H. ☐
4. From B: the **Windows key** opens Start on H; press it again (or Esc) to close it. ☐
5. Release everything (let go of Alt and the Win key, click on H's desktop). Nothing is stuck:
   Start is closed, no modifier is held, typing in a text box on H is normal. ☐
6. Ctrl+Alt+Del and Win+L from B do **not** reach H (Windows blocks them by design) — expected. ☐

## 2. User-launched from Program Files (should NOT grant)
Stop the service (`sc stop ShareCtrlScreenHost`), then start `sharectrl.exe` yourself by
double-clicking it in `C:\Program Files\ShareCtrlScreen\`.
1. `app.log` says **`UIAccess: not granted — the host was not started by the service`**. ☐
2. `sharectrl.exe --print-uiaccess` prints that line and exits **1**. ☐
3. The host otherwise works: share the screen, B can move the mouse and type on H. ☐
4. From B, Alt+Tab and the Windows key stay on **B** (they switch B's own windows / open B's
   own Start); H does not react. No stuck keys on either side. ☐

## 3. Portable copy (should NOT grant)
Copy `sharectrl.exe` to a non-secure folder (e.g. `%USERPROFILE%\Downloads\sct\`) and run it
there.
1. The host starts normally (portable mode). ☐
2. `app.log` / `--print-uiaccess` say **`not granted — the host was not started by the
   service`**, exit **1**. ☐
3. Same as 2.4: Alt+Tab and the Windows key stay local to B; H does not react; nothing stuck. ☐

## 4. Fallback — the flag could not be set
This is rare (the service runs as LocalSystem, which holds SeTcbPrivilege). It cannot be
forced from outside; observe it only if it happens. If the service could not enable the
privilege, duplicate the token or set the flag, then:
1. The host **still starts** (the service never refuses to launch it over this). ☐
2. `sharectrl-service.log` has **`launched engine pid=… in session … WITHOUT UIAccess
   (remote Alt+Tab and the Windows key will not reach the host's shell): <reason>`**, where
   `<reason>` names the step — e.g. the SeTcbPrivilege / LocalSystem message. ☐
3. `app.log` on H says `UIAccess: not granted — …`. ☐

## 5. The ignored unit test (run as SYSTEM, optional direct proof)
`elevation::uiaccess::tests::system_can_flag_the_console_users_token` is `#[ignore]`. On H,
with a user signed in at the console, build the test binary through the lane, then run that
binary as SYSTEM so `WTSQueryUserToken` and SeTcbPrivilege are available — e.g. Sysinternals
`psexec -s -w <native dir> cmd /c "<path to the elevation test exe> --ignored --nocapture
system_can_flag > %TEMP%\w5.txt 2>&1"` (or a one-shot scheduled task with `/ru SYSTEM`), then
`type %TEMP%\w5.txt`. Expect the test to pass: it duplicates the console user's token, sets
`TokenUIAccess`, reads it back as set, and confirms the original token is untouched. ☐
