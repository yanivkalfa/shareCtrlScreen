# W8 — Service-launched host: full fast path restored (DDA capture + HW encode)

Device-only. The regression reproduces ONLY for a host the SYSTEM service launched (route (a),
W4), on a real display. CI (headless runner, no service) cannot exercise Desktop Duplication or
the hardware MFT, so this checklist is the acceptance proof. Two Windows machines on different
networks: **B** the viewer (controls), **H** the host (machine A — the one the owner reported
was smooth self-launched and laggy once the service launched it). The lane proves only the
Rust/logic (error classification, retry wiring) and that Windows + WSL build clean.

What "works" means: a service-launched host captures via the fast DXGI path **and** encodes on
the hardware H264 MFT — the same fast path a self-launched host had — so the session is smooth,
and capture self-recovers across a UAC/lock-screen transition instead of ending.

The host log is `%APPDATA%\ShareCtrlScreen\app.log` on H. Confirm first it is a service launch:
the service line `launched engine pid=… in session 1 with UIAccess` and, near the top,
`UIAccess: granted` (W5). Everything below is read from this same running host instance.

## 1. Install as the service and connect
1. Install H with the W4 installer so `sharectrl-service.exe` sits next to `sharectrl.exe` and
   the `ShareCtrlScreenHost` service is RUNNING (it launches the host). Do NOT start the host by
   hand — that would be a self-launch and would not exercise the regression.
2. From B, connect to H with control and share H's primary display.

## 2. Fast capture path is in use (deliverable 1 + 2)
Read H's `app.log` for the session:
- [ ] There is a `capture: host thread attached to input desktop "Default"` line (the desktop
  name is normally `Default` while a user is at the desktop). This is the W8 attach.
- [ ] There is **no** repeating `DuplicateOutput1 failed (Access is denied. (0x80070005))`.
- [ ] There is **no** `host media loop ended: capture backend: Access is denied` and **no**
  `Screen sharing stopped` toast on B.
- [ ] `host: capture+encoder ready (<W>x<H> …)` appears once and stays (the loop is not
  restarting every second).

## 3. Hardware encoder is in use (widened goal — deliverable 3)
The owner reported this box was smooth self-launched, so the HW encoder is expected to work once
the capture thread (and the shared device) are on the input desktop.
- [ ] `encoder ready: H264 (hardware, …)` is present.
- [ ] There is **no** `hardware H264 encoder failed (0x8000FFFF)` and **no**
  `no hardware H264 encoder — using the software encoder (CPU)` line.
- If the HW line is still absent and the `0x8000FFFF` line is present on a confirmed service
  launch, capture the full `app.log` and report it: that would mean the HW-encode failure is NOT
  the desktop-context regression (contrary to the owner's self-launched baseline) and needs a
  separate root-cause pass — do not close W8 as done in that case.

## 4. The session is smooth (acceptance)
- [ ] Mouse movement and typing on B feel as responsive on H as a self-launched host was
  (no stutter, no lag building up). Compare against the owner's memory of the self-launched run.
- [ ] A moving window / scrolling text on H is fluid on B, not a slideshow.

## 5. Capture recovers across a secure-desktop transition (deliverable 2)
With the session live and controlled from B:
1. Trigger the secure desktop on H — press Ctrl+Alt+Del on H (or raise a real UAC prompt), then
   dismiss it; OR lock H (Win+L) and unlock it.
   - [ ] During the transition the log may show `host: screen capture lost … retrying until it
     returns` (a non-service host cannot read the secure desktop — that is expected and transient).
   - [ ] After returning to the desktop, `host: screen capture re-acquired after … — fast DDA
     path restored` appears and the session resumes on its own.
   - [ ] The host media loop did **not** end (no `Screen sharing stopped` toast); B did not have
     to reconnect.
2. [ ] Repeat the lock/unlock once more — recovery is reliable, not a one-shot.

## 6. No regression to elevated control (W4/W5 invariants)
- [ ] With "Capture keyboard shortcuts" on at B, Alt+Tab and the Windows key still act on H
  (W5 still passes — the desktop attach is on the capture thread only, not the injector thread).
- [ ] Clicking a UAC prompt on H from B still works (input still reaches the secure desktop).

Pass = sections 2, 3, 4, 5 all green and section 6 unchanged from W5. If section 3's HW line is
absent on a confirmed service launch, W8's capture half still passed but the HW-encode half is
open — report before closing.
